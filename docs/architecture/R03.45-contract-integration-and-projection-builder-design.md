# R03.45 Contract Integration & Projection Builder Design

- Version: 0.1
- Date: 2026-11-02
- Status: Design baseline + validation-only reference contract; production builder NOT IMPLEMENTED
- Parent gate: R03.44 CONDITIONAL_NOT_READY
- Primary risk: AUD-001 (Package Manifest → Resource Graph → Canonical Projection)
- Product code freeze: ACTIVE

## 1. Objective

Define the deterministic, read-only integration boundary that converts an ExperimentPackage Manifest and a pinned Resource Catalog Snapshot into:
1. a complete Package Resource Graph (R03.34);
2. the root dependency closure;
3. a Canonical Manifest Projection (R03.35);
4. an auditable projection report explaining every resolved reference.

This stage closes ambiguity in the integration contract. It does not close DEC-27/28/29, implement a production publisher/resolver, fetch resources, execute expressions, or authorize external access.

## 2. Verified current contract constraints

- ExperimentPackage schema is `contracts/experiment-package.schema.v1alpha1.json`.
- Direct resource references for model/scene/instrument/workflow/rubric carry `id/version/digest`; they do not carry storage, URI, media type, byte size, or license metadata.
- Package assets carry id/mediaType/digest/licenseId/source and optional sizeBytes; they do not carry version or storage location.
- ScientificModel equation/constraint/validation references can introduce transitive Expression and validation resources.
- Resource Graph requires node type/version/digest/storage and graph edges; Canonical Projection requires a normalized resource path, media type, size and license.
- Consequently, neither the Manifest alone nor the existing Resource Graph fixture can safely supply all projection inputs.

## 3. Normative input model

### 3.1 Package Manifest

The Manifest remains the business-authoritative source for:
- package identity: apiVersion, metadata.id, metadata.version;
- semantic content: metadata and spec, excluding only fields explicitly declared envelope/volatile by a future approved projection profile;
- direct role references: model, scene, instruments, workflow, assessment.rubric;
- asset declarations: id, mediaType, digest, licenseId, source, optional sizeBytes.

The builder MUST validate the Manifest against the existing ExperimentPackage schema before projection. It MUST NOT silently fill missing business fields or normalize user-authored semantic values.

### 3.2 Immutable Resource Catalog Snapshot

A separate, immutable catalog snapshot supplies fields absent from the Manifest:
- exact identity: resource_type, resource_id, version, digest;
- storage: embedded/external/restricted;
- URI or package-relative path;
- media_type, size_bytes, license_id;
- zero or more typed dependency references;
- optional resource-document metadata needed to verify Model expression references.

Catalog records are keyed by (resource_type, resource_id, version). A key may map to exactly one digest. Conflicting metadata for the same key is a hard error. The snapshot is an explicit builder input and MUST be pinned by its own immutable revision/digest by the eventual publisher; catalog revision format remains OPEN.

The catalog is metadata, not proof that the referenced bytes exist or match their declared digest. Byte-level verification belongs to the isolated package ingestion/content-addressing layer.

### 3.3 Root resource identity and digest-cycle prevention

The root graph node represents the Manifest artifact. Its node digest is the digest of the exact source Manifest bytes (or a future explicitly versioned source-byte representation), not the final Canonical Package Digest.

The root node is a graph traversal anchor only. It MUST be excluded from Canonical Projection `resources` and `dependency_closure`; otherwise the final Package Digest would recursively depend on itself. The root node digest and final package digest are different values with different purposes.

No digest may be fabricated when source bytes are unavailable. A builder invoked with an in-memory parsed object must receive a separately verified source-manifest digest.

## 4. Deterministic mapping rules

### 4.1 Root and direct edges

- Root ID: `package:{metadata.id}@{metadata.version}`.
- Root type: `package`.
- Add one direct edge for each declared role reference using relation `requires`.
- Role-to-type mapping is fixed: model→model, scene→scene, instruments[]→instrument, workflow→workflow, assessment.rubric→rubric, assets[]→asset.
- Each direct reference MUST match exactly one catalog entry by type + ID + version + digest.
- Asset version is supplied by the catalog because the current Manifest asset shape has no version field; the asset ID, digest, media type and license ID MUST agree with the Manifest.

### 4.2 Transitive dependencies

- The catalog's dependency list is authoritative for resource-to-resource edges not represented in the Package Manifest.
- A ScientificModel resource document MUST be checked against its declared resource references. Every equations[].expressionRef, constraints[].expressionRef (when present), and validationCases[] reference MUST resolve to the matching catalog resource identity and digest.
- Model-to-Expression edges use relation `requires`.
- Dependencies are recursively expanded until closure; cycles, missing entries, duplicate identities and digest conflicts reject the entire projection.
- A catalog dependency that is not reachable from the Package root is not included. The builder MUST NOT include arbitrary catalog records.

### 4.3 Storage policy

R03.34 path/URL/restricted policy validation remains authoritative. External resources are never fetched by the builder. Restricted resources require access_policy_id and an explicit policy decision; the builder does not grant runtime access.

### 4.4 Canonical Projection

- `package` derives from Manifest apiVersion/id/version.
- `content` derives from an explicit semantic-field projection of the Manifest; no generic recursive removal of keys named timestamp/signature/digest is permitted.
- `resources` contains all reachable non-root resource records, exactly once, with normalized path/type/id/version/media type/size/digest/license.
- `dependency_closure` contains all reachable non-root resource identities, exactly once.
- R03.35 ordering rules apply after graph validation.
- The projection builder MUST NOT choose JCS or CBOR. Serialization profile and domain-separated digest remain downstream responsibilities.

## 5. Required rejection conditions

| Error | Condition |
|---|---|
| MANIFEST_SCHEMA_INVALID | Manifest fails the existing schema |
| RESOURCE_REF_NOT_FOUND | No catalog entry matches declared type/id/version |
| RESOURCE_DIGEST_MISMATCH | Identity matches but digest differs |
| RESOURCE_METADATA_MISMATCH | Asset metadata conflicts with catalog |
| DUPLICATE_CATALOG_IDENTITY | Duplicate logical identity in snapshot |
| CONFLICTING_CATALOG_DIGEST | Same logical identity maps to different digest |
| TRANSITIVE_DEPENDENCY_MISSING | A dependency cannot be resolved |
| MODEL_EXPRESSION_REF_MISMATCH | Model document ref and catalog identity disagree |
| DEPENDENCY_CYCLE | Reachable dependency cycle |
| RESOURCE_POLICY_REJECTED | Storage/path/host/restricted policy fails |
| SOURCE_MANIFEST_DIGEST_REQUIRED | Exact source bytes digest is unavailable |

Errors MUST identify a stable code and a safe resource path/identity; do not echo secrets or signed external URLs into public logs.

## 6. Determinism and immutability invariants

1. Same Manifest bytes + same catalog snapshot + same policy inputs → byte-for-byte identical Graph and Projection data structures.
2. Input array order does not affect Graph node/edge ordering or Canonical Projection ordering.
3. Every emitted non-root graph node appears exactly once in the projection.
4. Every projection dependency appears in the graph closure; no unreachable catalog record appears.
5. Every direct Manifest reference is represented by exactly one root edge.
6. Every Model expression reference is represented by a Model→Expression edge.
7. Input objects are not mutated.
8. No network, filesystem traversal outside the supplied package root, expression execution, plugin execution, or arbitrary code execution occurs.
9. Graph root digest is source-manifest digest; it is not the final canonical package digest.
10. Serialization candidate selection is not part of this builder.

## 7. Security and trust boundaries

The Resource Catalog Snapshot is untrusted input until validated. A catalog entry does not prove byte existence, authenticity, license rights, or authorization. The builder must not follow catalog URLs. External content retrieval, DNS/IP SSRF controls, digest verification, signature verification, provenance, and license policy enforcement are separate gates.

The builder's output is suitable for deterministic review and downstream validation only. It is not a signed release artifact.

## 8. Validation plan

The validation-only reference implementation will cover:
- schema-valid Manifest + catalog → expected graph/projection;
- direct role mapping and asset metadata reconciliation;
- transitive dependency closure and Model expression binding;
- shuffled catalog/dependency order invariance;
- missing reference, digest mismatch, metadata mismatch, duplicate identity, cycle and unreachable catalog records;
- missing source Manifest digest;
- input immutability and no network side effects.

Golden vectors in this stage prove one Python reference implementation only. Cross-language byte-for-byte interoperability remains Not Tested until a second independent implementation is available.

## 9. Decision impact

- ADR-011/012 remain accepted design rules.
- Canonical Projection structure/order follows R03.35.
- DEC-27 remains OPEN: JCS vs Deterministic CBOR and digest profile are not selected.
- DEC-28 remains OPEN: no production signing/verification or trust-root decision.
- DEC-29 remains OPEN: no legal license determination or complete SPDX policy.
- DEC-08/09/10/17 remain OPEN.

## 10. Exit criteria

R03.45 is complete when the input boundary, mapping rules, root digest semantics, cycle prevention, deterministic output invariants and rejection taxonomy are documented and represented by machine-readable fixtures.

AUD-001 is NOT CLOSED by this design stage. It can be downgraded only after a reference implementation passes CI against the full Manifest/Model/Resource Catalog fixtures, and closed only after production ingestion integration plus cross-language golden vectors and content-byte verification.
