# R03.16 API与事件契约样例集（规范草案）

- 版本：0.1；日期：2026-11-02
- 状态：示例契约；正式OpenAPI/AsyncAPI生成前需评审
- 关联：R03.10、R03.14、R03.15

## 1. 通用约定

- Base path：/v1
- Content-Type：application/json
- 时间戳：RFC3339 UTC
- ID：不透明稳定标识
- tenant_id、actor_id：服务端认证上下文派生
- 写操作：Idempotency-Key；Runtime命令还需If-Match或expected_state_version
- 错误：稳定code、correlation_id和retryable
- 分页：cursor-based，响应包含next_cursor

## 2. 创建Session请求/响应

请求：POST /v1/sessions
Header：Idempotency-Key: <client-generated-key>

请求字段：
- assignment_id
- experiment_instance_id（如已创建）
- package_version_id
- client_context（仅非敏感客户端信息）

服务端必须验证Assignment归属、开放时间、尝试次数、Package发布状态和Tenant权限。客户端不能指定tenant_id或actor_id。

响应字段：
- session_id
- status
- state_version
- package_digest
- model_version_id
- created_at
- correlation_id

## 3. Runtime Command请求/响应

请求：POST /v1/sessions/{session_id}/commands
Headers：Idempotency-Key、If-Match: "<state_version>"

Body：
- command_type
- schema_version
- payload

成功响应：
- command_receipt_id
- command_id
- outcome
- session_status
- state_version
- accepted_at
- correlation_id

冲突响应：
- code=STATE_VERSION_CONFLICT
- current_state_version
- current_status
- retryable=false

同Key同Hash返回原Receipt；同Key不同Hash返回IDEMPOTENCY_KEY_REUSE_CONFLICT。服务端必须将Receipt、状态、事件和Outbox原子提交。

## 4. Observation响应

Observation最小字段：
- observation_id
- session_id
- execution_id（可空，按来源）
- quantity_id
- value或value_ref
- unit
- simulation_time
- simulation_time_unit
- observed_at
- source_type/source_id
- model_version_id
- quality_status
- schema_version

时间序列较大时返回Dataset引用、digest、行数/样本数和短期下载授权，不将超大数组内嵌普通API响应。

## 5. 事件信封JSON样例

~~~json
{
  "event_id": "evt_example",
  "event_type": "SessionStarted",
  "schema_version": "1.0",
  "tenant_id": "tenant_example",
  "aggregate_type": "RuntimeSession",
  "aggregate_id": "session_example",
  "aggregate_sequence": 4,
  "state_version": 3,
  "epoch": 2,
  "occurred_at": "2026-11-02T08:00:00Z",
  "correlation_id": "corr_example",
  "causation_id": "cmd_example",
  "payload": {
    "execution_id": "exec_example",
    "package_digest": "sha256:example"
  }
}
~~~

样例中的ID和digest均为占位值，不是生产格式或真实凭证。

## 6. 事件消费者规则

1. 先校验schema_version和必需字段。
2. 记录event_id和aggregate_sequence处理位置。
3. 已处理event_id直接幂等确认。
4. aggregate_sequence小于等于已处理位置时不重复应用。
5. 发现序号缺口时暂停该聚合后续应用并执行补拉/重放。
6. 消费者副作用必须有自己的幂等键。
7. 重放模式不得重复发送通知、创建Execution或重复发布成绩。

## 7. 错误响应样例

~~~json
{
  "error": {
    "code": "STATE_VERSION_CONFLICT",
    "message": "The session has changed. Refresh the current state.",
    "correlation_id": "corr_example",
    "retryable": false,
    "current_version": 12
  }
}
~~~

不得在错误消息中返回SQL、堆栈、内部网络地址、Token或其他租户资源信息。

## 8. OpenAPI必须补齐的细节

正式规范需要为每个端点补齐：认证Scheme、角色/资源权限、请求/响应Schema、错误响应、幂等策略、限流、分页、版本兼容、数据分类、审计事件和Contract Test。样例不替代完整OpenAPI文件。
