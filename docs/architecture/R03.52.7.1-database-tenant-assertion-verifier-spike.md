# R03.52.7.1 — PostgreSQL Database-Side Tenant Assertion Verifier Spike

- Date: 2026-11-02
- Status: PASS (executable reference spike); production security gates OPEN
- Decision: DEC-19 target architecture is ACCEPTED; production security gates remain OPEN
- Product Code Freeze: ACTIVE; P3.17: OUT OF SCOPE
- Production readiness: NOT ESTABLISHED

## 1. Objective

Prove that PostgreSQL RLS can validate a signed, scoped tenant assertion without trusting a caller-controlled tenant GUC, while an ordinary runtime role cannot read or modify the verifier key or replace the verifier function.

This spike is intentionally narrower than a production security implementation. It uses a protected HMAC-SHA256 key and PostgreSQL pgcrypto. The test issuer shares the key only inside the disposable CI fixture.

## 2. Implemented candidate

The executable harness is `scripts/test_postgres_tenant_assertion_verifier.py`.

- A NOLOGIN, NOSUPERUSER, NOBYPASSRLS verifier-owner role owns a protected schema and signing-key table.
- The ordinary runtime role receives schema USAGE and EXECUTE on one verifier function, but no key-table privileges, schema CREATE, table ownership, BYPASSRLS, or membership in the verifier-owner role.
- A SECURITY DEFINER PL/pgSQL function has a fixed search_path (`pg_catalog` plus the protected schema), uses schema-qualified key and pgcrypto references, rejects malformed/oversized tokens, validates the HMAC, exact claim set, claim types, maximum lifetime, expiry, audience, action, tenant and resource.
- The function returns false on malformed input or verifier errors. It does not expose key material.
- RLS SELECT and UPDATE policies invoke the verifier using the row's tenant_id and resource ID. A caller-set `app.tenant_id` has no authorization effect.
- The verifier owner is NOLOGIN and not granted to runtime. Runtime cannot read/update the key, replace the function, or SET ROLE to the verifier owner.

Assertion claim profile in this spike: `v, tenant_id, sub, aud, action, resource_id, iat, exp, nonce`. Token lifetime is capped at 120 seconds. A valid assertion authorizes only the exact tenant/action/audience/resource tuple.

## 3. Adversarial tests

The CI harness covers:

1. Valid assertion reads only its exact tenant resource.
2. Missing assertion fails closed.
3. Modified signature fails closed.
4. Tenant claim mutation without re-signing fails closed.
5. A valid tenant-A assertion cannot read tenant B even if `app.tenant_id` is set to B.
6. An assertion cannot be replayed against another resource.
7. Audience and action mismatch fail closed.
8. Expired and future-issued assertions fail closed.
9. UPDATE requires an update-scoped assertion; a read assertion cannot mutate.
10. Runtime cannot SELECT or UPDATE signing-key material.
11. Runtime cannot replace the SECURITY DEFINER verifier.
12. Runtime cannot assume verifier-owner role, is not superuser/BYPASSRLS, and does not own the protected data table.

The earlier GUC-only vulnerability reproduction remains in place as a separate control test.

## 4. Security properties and limits

### Demonstrated if CI passes

- The RLS decision is based on database-side signature verification, not a plain tenant GUC.
- A caller without the signing key cannot alter the tenant/action/resource claims and preserve a valid signature.
- The runtime role cannot directly read or mutate the verifier key using its granted database privileges.
- The runtime role cannot replace the verifier function under the tested grants.
- The same signed assertion is resource-scoped; it is not a tenant-wide bearer token.

### Explicitly not demonstrated

- Production issuer isolation, authentication/membership enforcement, key custody, KMS/HSM integration, key rotation or emergency revocation.
- Single-use nonce consumption or durable replay prevention. The nonce is integrity-protected but not consumed in this spike; the short expiry and exact scope are not a substitute for replay-state semantics where one-time use is required.
- Constant-time behavior audit of the complete database execution path.
- Asymmetric signature verification. HMAC requires the issuer and verifier to share a secret; this is a constrained fallback, not the preferred separation of signing and verification authority.
- Protection against database superuser/host compromise, verifier-owner compromise, malicious trusted administrators, or unreviewed SECURITY DEFINER/privileged paths elsewhere in the database.
- Full Job/lease owner/epoch verification through a production Store adapter, connection-pool cancellation/reset behavior, migration lifecycle, failover, load, or multi-process Worker behavior.

## 5. Production design decision still required

The target architecture prefers asymmetric signatures so the database holds only a public verification key. This spike uses pgcrypto HMAC because it is available in the PostgreSQL CI image and permits an executable proof of protected database-side verification.

Before production selection, compare:
- a vetted PostgreSQL extension or reviewed native verifier supporting asymmetric signature verification;
- a narrowly isolated database-verifier service/gateway whose credential boundary is not available to the ordinary application role;
- the protected HMAC verifier demonstrated here, including the shared-secret blast radius and operational key custody.

Do not copy the fixture key model into production without an explicit security review. If a shared secret is selected, the issuer and verifier custody, rotation, revocation, access path, audit and incident procedure must be approved.
