# R03.51 PostgreSQL Concurrency & Transaction Model

- Status: Reference SQL + integration harness; CI verification pending
- Isolation target: READ COMMITTED
- Lease clock: PostgreSQL clock_timestamp()

## Claim query

```sql
SELECT job_id, status, attempt_count, maximum_attempts, lease_epoch
FROM ingestion_jobs
WHERE tenant_id = :tenant
  AND ((status IN ('queued','retry') AND available_at <= clock_timestamp())
    OR (status='running' AND lease_expires_at <= clock_timestamp()))
ORDER BY priority DESC, available_at, created_at, job_id
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

The row lock protects candidate selection until owner, expiry, attempt count and epoch are written and committed. No handler execution or network I/O occurs while the lock is held. Other workers skip locked rows and may claim different jobs.

## Renewal/completion/reclaim race

Renewal and completion serialize on the Job row. Renewal succeeds only if the lease is still valid and owner/epoch match. Completion succeeds only if the lease remains valid at its database check. If completion commits first, renewal sees a terminal job and fails. If renewal commits first, completion may proceed with the same epoch and extended expiry. If reclaim commits first, epoch increments and the old completion fails.

## Completion transaction

Lock order is Job -> Session -> Receipt -> Transition -> Outbox. Check Session expected_revision; update Session; insert deterministic completion Receipt; append immutable Transition; insert R03.50 session Outbox; update Job to succeeded; commit. Any failure rolls back all writes. Handlers must not introduce an inverse Session -> Job lock order.

## Retry and DLQ transaction

Failure handler locks Job and verifies current unexpired lease. Retry sets retry + available_at and clears lease. Permanent error or maximum attempts sets dead_lettered and inserts DLQ record atomically. A crash before commit leaves the job running until lease expiry; a crash after commit leaves durable retry/DLQ state.

## Deadlocks and indexes

- Claim locks one Job row only.
- Partial active uniqueness prevents duplicate active Job Types per Session.
- Separate partial indexes support due queued/retry and expired running scans.
- Keep transactions bounded; never call network services while holding row locks.
- Priority order can starve low-priority work; fairness policy needs workload evidence.

## Tenant boundary

Queries include tenant_id and run under RLS. app.tenant_id GUC is not an independent security boundary; DEC-19 remains OPEN. The test role is NOLOGIN/NOSUPERUSER/NOBYPASSRLS. Production roles, grants, connection-pool reset and trusted tenant context are not selected.

## Failure matrix

| Failure point | Durable result |
|---|---|
| before claim commit | no lease |
| after claim commit / worker crash | running until DB expiry; reclaim increments epoch |
| handler partially executes | at-least-once replay possible; side effects need idempotency |
| before retry commit | still running; expiry/reclaim path |
| after retry commit | retry and available_at durable |
| Outbox insert failure | Session, Transition and Job completion roll back |
| old worker completes after reclaim | stale epoch rejected |
| duplicate completion | no second side effect |

At-least-once execution is not exactly-once. Fencing protects only resources that validate the token.
