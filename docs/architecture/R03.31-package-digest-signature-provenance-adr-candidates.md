# R03.31 Package确定性Digest、签名与Provenance决策候选

- 版本：0.1；日期：2026-11-02
- 状态：方案比较与Spike计划；DEC-27/28/29保持OPEN
- 关联：R03.8、R03.20 DEC-27/28/29、R03.30

## 1. 问题定义

R03.30验证了一个本地Asset的字节SHA-256、sizeBytes和路径安全，但仍未定义顶层Package Digest、跨平台规范化、发布者签名、密钥撤销和License/Provenance证据。

内容寻址证明内容是什么；数字签名证明哪个受信任主体批准了这个Digest；License/Provenance证明内容来源与使用权依据。三者不能互相替代。

## 2. 顶层Package Digest候选

| 方案 | 方法 | 优点 | 风险 |
|---|---|---|---|
| A | RFC 8785 JSON Canonicalization Scheme（JCS）+资源清单 | 与现有JSON Schema自然衔接、易审计 | 必须严格处理数字、Unicode、字符串和YAML解析语义 |
| B | Canonical CBOR +资源清单 | 二进制结构紧凑 | 引入额外工具链和跨语言互操作测试 |
| C | 确定性归档文件Digest | 可直接对归档求摘要 | 时间戳、文件顺序、权限位、压缩器版本和平台差异会改变归档字节 |

候选建议：优先Spike方案A，即JCS Manifest/Index + 每个资源独立SHA-256。若跨语言实现无法保证字节一致，再比较Canonical CBOR。DEC-27仍OPEN，不得把建议写成已批准选型。

## 3. Package Index逻辑结构

~~~json
{
  "package_schema_version": "v1alpha1",
  "package_id": "example.dc-series",
  "package_version": "1.0.0",
  "manifest_digest": "sha256:<64-hex>",
  "resources": [
    {
      "path": "assets/fixture.json",
      "media_type": "application/json",
      "size_bytes": 78,
      "digest": "sha256:<64-hex>",
      "license_id": "internal-test-fixture"
    }
  ]
}
~~~

候选约束：
- 资源路径统一为POSIX相对路径，拒绝绝对路径、盘符、反斜线、父目录跳转、重复规范化路径和大小写冲突；
- 资源按规范化路径排序，同一路径只能出现一次；
- 资源Digest按原始字节计算；
- Manifest canonical bytes和Resource Index分别有Digest；
- 顶层Digest覆盖Schema版本、Package ID/Version、Manifest Digest和完整Resource Index；
- 不将临时本地路径、外部URL或运行时随机值写入canonical index；
- License/Provenance是否进入内容Digest或签名Attestation由DEC-28/29明确。

## 4. Signature / Attestation候选

签名消息至少绑定package_digest、package_id、package_version、canonicalization_algorithm、digest_algorithm、signer identity、key/certificate identity、created_at、validation_report_digest、approval reference和envelope version。

候选方向：
- KMS/HSM托管非导出私钥；
- DSSE/in-toto风格的声明封装；
- Sigstore Keyless或企业身份绑定签名；
- 验证器支持证书链、OIDC身份、时间戳、撤销和信任策略。

暂不指定供应商、算法组合或身份提供商。签名私钥不得放入Package、Git仓库、客户端或普通CI日志。

## 5. License / Provenance候选

每个可再分发Asset记录SPDX License Identifier或受控自定义许可ID、来源/作者/供应商、版权署名、修改/商用/再分发权、许可证据引用、审核人/时间/批准状态及撤回/到期/地域限制。

未知、缺失或冲突许可不得静默视为可商用。合同正文和个人信息不应写入公开Manifest，应使用受控License Evidence ID。

## 6. 必须执行的Spike

| ID | 测试 | 通过标准 |
|---|---|---|
| PKG-DIG-01 | 两种语言对同一Manifest执行canonicalization | 字节输出完全一致 |
| PKG-DIG-02 | 对象键顺序/空白/换行扰动 | canonical bytes与Digest不变 |
| PKG-DIG-03 | Unicode与数字边界 | 按选定规范产生唯一结果 |
| PKG-DIG-04 | 资源列表顺序扰动 | 顶层Digest不变 |
| PKG-DIG-05 | 任一资源字节改变 | 对应资源Digest与顶层Digest改变 |
| PKG-DIG-06 | 路径穿越/大小写冲突/重复路径 | 发布前拒绝 |
| PKG-SIG-01 | 有效签名与身份链 | PASS |
| PKG-SIG-02 | 内容修改后旧签名 | REJECT |
| PKG-SIG-03 | 密钥撤销/过期/错误Issuer | REJECT |
| PKG-SIG-04 | 历史版本签名验证 | 可审计复现 |
| PKG-LIC-01 | 未知/缺失License | BLOCK RELEASE |
| PKG-LIC-02 | 禁止商用/再分发许可 | BLOCK RELEASE |
| PKG-LIC-03 | 许可例外审批 | 必须有授权记录和范围/到期 |

## 7. 决策与治理

- DEC-27：Canonicalization和顶层Digest算法，OPEN；
- DEC-28：Signature/Attestation格式、信任根、密钥生命周期，OPEN；
- DEC-29：SPDX映射、许可策略和证据保留，OPEN。

在三项决策完成前，不得宣称Package已具有顶层完整内容Digest、可信发布签名或商用/再分发授权。W2.1继续IN PROGRESS，G3/G4保持BLOCKED。

## 8. 结论

本文件给出可验证的候选路径，建议先执行JCS + Resource Index Spike，但不替产品、安全或法律负责人作出选型决定。R03.30单Asset完整性验证是必要的低层基础，不等同于Package整体内容寻址、签名和许可发布闭环。
