## 1. Purpose

Separate CI smoke checks from decision-grade driver/pool performance measurements. The benchmark script now supports two explicit profiles:

| Profile | Default concurrency | Iterations per worker | Repetitions | Evidence |
|---|---|---:|---:|---|
| `smoke` | 1, 8, 32 | 20 | 1 | Functional CI smoke only |
| `controlled` | 1, 8, 32, 64, 128 | 100 | 5 | Candidate performance evidence only when runner/database environment is controlled and reviewed |

The controlled profile does not itself provision or enforce host resources. It requires an operator-supplied environment ID, declared CPU limit and memory limit, and records observed platform/cgroup/PostgreSQL settings. The operator remains responsible for enforcing the stated limits.

## 2. Configuration

Required for both profiles:
- `DATABASE_URL`: disposable PostgreSQL database with the pinned pgsodium extension.
- `STORE_BENCH_ENV_FILE`: private temporary JSON path used to pass short-lived assertion tokens and DB connection parameters to the Node.js child process.
- `STORE_BENCH_NODE_OUTPUT`: private temporary Node.js result path.
- `STORE_BENCH_OUTPUT`: result JSON output path.

Controlled profile additionally requires:
- `STORE_BENCH_ENVIRONMENT_ID`: stable name/ID for the benchmark host and database deployment.
- `STORE_BENCH_RUNNER_CPU_LIMIT`: declared CPU quota or pinned core count.
- `STORE_BENCH_RUNNER_MEMORY_MB`: declared memory limit.

Optional overrides:
- `STORE_BENCH_CONCURRENCY_LEVELS` (comma-separated; default by profile)
- `STORE_BENCH_ITERATIONS_PER_WORKER`
- `STORE_BENCH_REPETITIONS`
- `STORE_BENCH_POOL_MIN`
- `STORE_BENCH_POOL_MAX`

All configuration is validated before the workload starts. Each measured case receives a fresh short-lived signed tenant assertion; assertion tokens are written only to the private runner-temp handoff file and are not included in the uploaded result artifact.

## 3. Controlled run procedure

1. Provision a dedicated benchmark host/VM. Record CPU model, core allocation, RAM, kernel/OS, hypervisor/container runtime and storage class.
2. Enforce a fixed CPU and memory quota for the benchmark process and PostgreSQL. Pin CPU affinity where supported. Do not run unrelated workloads.
3. Use a dedicated PostgreSQL 17.11 + pgsodium 3.1.11 environment with a fixed configuration and dataset. Record PostgreSQL settings in the emitted manifest.
4. Keep the client-to-database network path fixed; record whether the path is direct, PgBouncer session pooling or transaction pooling. Do not mix modes in one comparison.
5. Install exact dependency versions from the repository's pinned requirements and benchmark workflow. Record lockfile and commit SHA.
6. Run the controlled profile and retain the raw JSON artifact. Repeat the entire experiment on at least two separate time windows/host reboots before selecting a candidate.
7. Review median and spread across five repetitions. Reject runs with unexpected CPU throttling, memory pressure, background load, DB restarts or material environment drift.

Example invocation (Linux runner; paths are illustrative local paths, not repository artifacts):

```bash
export DATABASE_URL='postgresql://benchmark_admin:REDACTED@127.0.0.1:5432/stemlab_bench'
export STORE_BENCH_PROFILE=controlled
export STORE_BENCH_ENVIRONMENT_ID='bench-host-a-pg17-direct-2026-11'
export STORE_BENCH_RUNNER_CPU_LIMIT='4 pinned vCPU'
export STORE_BENCH_RUNNER_MEMORY_MB=8192
export STORE_BENCH_POOL_MIN=2
export STORE_BENCH_POOL_MAX=32
export STORE_BENCH_ENV_FILE=/tmp/store-bench-env.json
export STORE_BENCH_NODE_OUTPUT=/tmp/store-bench-node.json
export STORE_BENCH_OUTPUT=/tmp/store-bench-results.json

taskset -c 0-3 python scripts/benchmark_store_driver_pool.py
```

The CPU affinity example assumes Linux CPU IDs 0–3 are assigned to the benchmark process. Adjust to the actual isolated CPU set; do not copy it blindly.

## 4. Result manifest

The JSON output records:
- profile, concurrency levels, iterations, repetitions and pool bounds;
- OS, architecture, Python/Node versions, logical CPU count and detected CPU model;
- cgroup v2 CPU/memory limits when available and operator-declared resource limits;
- PostgreSQL server version, max_connections, shared_buffers, work_mem, effective_cache_size and track_io_timing;
- per-driver/per-concurrency/per-repetition throughput, p50/p95/p99 latency and pool acquisition wait percentiles.

No assertion, password or connection string is emitted into the result artifact.

## 5. Interpretation and acceptance rules

- Smoke profile is not suitable for performance ranking.
- Controlled profile is necessary but not sufficient: it must pass environment review, workload conformance, repeated-run stability and fault/correctness gates.
- Compare candidates only under identical PostgreSQL, pooler, schema, indexes, data volume, tenant verifier, assertion semantics, transaction isolation and operation mix.
- Report per-run values and aggregate median/spread; do not average unlike environments.
- A higher throughput result is not acceptable if it increases stale lease acceptance, transaction outcome ambiguity, tenant-context leakage, deadlocks, invariant violations or tail latency beyond the approved SLO.
- Candidate selection remains blocked until DEC-03 runtime and DEC-14 deployment/provider decisions are made.

## 6. Remaining benchmark gaps

This harness still measures a simple RLS-protected row read. The next increment must implement the full Store operation mix and fault matrix:
- Claim with SKIP LOCKED, lease owner/expiry and epoch increment;
- Renew with DB-clock fencing;
- Complete with Job -> Session -> Receipt -> Transition -> Outbox lock/write order and atomic commit;
- Fail/retry and DLQ transitions;
- tenant contention, hot queue and multi-tenant fairness;
- cancellation during query/COMMIT/release, connection loss, DB restart and pool exhaustion;
- ambiguous commit reconciliation and duplicate idempotency;
- connection reuse across tenant assertions after commit/rollback/cancellation;
- selected pooler/proxy mode compatibility.

The harness capability is implemented, but no controlled benchmark has yet been run and no production driver/pool is selected.
