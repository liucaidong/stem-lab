## 1. Executive determination

PR #18 and PR #19 provide useful independent PostgreSQL conformance primitives. They do not yet establish a v2alpha2 business Handler path.

The existing resource-authorization fixture is a separate legacy assertion path. Its verifier is `verify_v2` and its authorization entry is `authorize_v2`; it does not call `verify_request_assertion_v2alpha2`, `assert_request_digest_v2alpha2`, or either Receipt v2alpha2 function. The v2alpha2 functions are not wired into renew/fail/retry/dead-letter, Receipt reconciliation, Outbox dispatch or Outbox acknowledgement.

Therefore:
- Digest-to-actual-mutation binding: **NOT IMPLEMENTED / BLOCKED**.
- Receipt v2alpha2 business integration: **NOT IMPLEMENTED / BLOCKED**.
- v2alpha2 durable Nonce Ledger and cross-version coordination: **NOT IMPLEMENTED / BLOCKED**.
- Complete Job/Transition/Outbox UOW under v2alpha2: **NOT IMPLEMENTED / BLOCKED**.
- R03.52.7.3.11.4 remains **BLOCKED**.

## 3. Call graph and transaction boundary observed

### 3.1 v2alpha2 helper path

```text
test / caller
  -> verify_request_assertion_v2alpha2(payload, signature, operation_arguments)
       -> strict raw JSON parser
       -> issuer_keys lookup
       -> Ed25519 verification over raw payload bytes
       -> assert_request_digest_v2alpha2(claim, operation_arguments)
            -> request_digest_v2alpha2(envelope)
  -> returns Claim
```

No subsequent business mutation function is called by this path. The SQL argument object is supplied by the caller and is not the same local variable/parameter set as a business UPDATE/INSERT.

### 3.2 Receipt helper path

```text
test / caller
  -> reserve_request_receipt_v2alpha2(identity, digest, resource)
       -> INSERT ... ON CONFLICT (tenant, action, idempotency_key)
       -> lock/read existing Receipt and compare digest
  -> finalize_request_receipt_v2alpha2(receipt_id, terminal_status, outcome)
```

No Job row, Nonce Ledger, Transition or Outbox mutation is included in either function.

### 3.3 Existing legacy action path

The resource-authorization fixture uses:
- Runtime -> `renew_v2`, `fail_v2`, `retry_v2`, `dead_letter_v2`;
- Dispatcher -> `dispatch_outbox_v2`, `ack_outbox_v2`;
- Replay -> `replay_dlq_v2`;
- Runtime direct RLS-governed writes for the Complete path.

These paths call the legacy `verify_v2`/`authorize_v2`, not the v2alpha2 verifier. The legacy nonce ledger is transaction-bound through `pg_current_xact_id()`. This is useful existing evidence, but it is not evidence of v2alpha2 nonce coordination.

The Complete path is materially different: Runtime has narrowly column-granted Job UPDATE and INSERT grants for Receipt/Transition/Outbox, with RLS policies calling `assertion_allows`. The fixture demonstrates row-scope checks, but it does not provide one mandatory database function that requires the entire Complete write set to succeed together. A caller can issue the statements separately unless a higher-level transaction contract is enforced.

## 4. Findings requiring remediation

### F-01 — No explicit v1alpha1/v2alpha2 dispatch at operation entry

The legacy `verify_v2` entry and the v2alpha2 verifier are separate functions, but no common action entry point selects exactly one verifier from an explicit contract discriminator. No fallback behavior is observed in the audited handlers because the new verifier is not wired at all.

**Required:** a single fail-closed dispatch boundary that parses the version discriminator and routes to exactly one version-specific verifier; v1alpha1 behavior remains unchanged.

### F-02 — Digest arguments are not bound to actual SQL mutation arguments

The v2alpha2 verifier accepts a JSON argument object separately from business SQL parameters. Existing handlers accept their own parameters (for example lease duration, retry delay/error code, dead-letter error/reason), while the digest verifier is not called from them.

**Required:** each action handler must build its digest argument representation from the exact typed local parameters used in the mutation statements. The verified Claim supplies immutable identity fields; caller-supplied tenant/job/session/resource identities must not override them.

### F-03 — Receipt helper is not an integrated Unit of Work

The Receipt functions do not consume a verified Claim, acquire/validate the Job fence, write Nonce Ledger, mutate Job, append Transition, or insert Outbox. The helper tests cannot establish that a successful Receipt implies all business writes.

**Required:** reserve/reconcile Receipt inside the same handler transaction as Nonce, Job, Transition and Outbox; same-key/same-digest replay returns the stored terminal outcome without reapplying effects.

### F-04 — Receipt test uses an identity-inconsistent replay fixture

The helper test reserves the original Receipt with `operation-1`, then submits the same idempotency key and constant digest with `operation-retry`, and expects the original Receipt. The concurrent test similarly varies operation IDs while holding the digest constant.

The canonical Request Envelope includes `operation_id`. Therefore a correctly recomputed digest for a different operation_id must differ. The current fixture bypasses that relationship by reusing a literal digest.

**Required:** change replay fixtures to use the same operation_id when replaying the same signed request, and add negative tests where operation_id/resource identity changes while digest is held constant at the helper boundary. The integrated Handler must never accept such a disconnected identity/digest tuple.

### F-05 — Legacy Nonce Ledger does not prove v2alpha2 cross-version replay isolation

The existing `authorize_v2` writes a nonce row keyed by (issuer, kid, nonce) and binds it to transaction/token. It validates a legacy claim shape without the v2alpha2 `contract_version` and `request_digest` contract. No v2alpha2 handler currently writes to a coordinated version-aware ledger.

**Required:** define one durable nonce uniqueness domain or a rigorously proven version-aware key policy, and test same nonce across versions, actions, tenants, handlers, transactions and connections. Do not alter v1alpha1 semantics without compatibility proof.

### F-06 — Legacy handlers have mixed write/error boundaries

The legacy renew/fail/retry/dead-letter/outbox functions use SECURITY DEFINER functions with exception handling that returns NULL/false. PL/pgSQL exception blocks roll back statements inside the protected block, but a false/null return is not itself proof that a caller cannot commit earlier independent writes in the same outer transaction.

The Complete path permits multiple RLS-protected statements rather than requiring a single complete write-set operation.

**Required:** the v2alpha2 UOW must raise a typed exception to abort the outer transaction or enforce a mandatory rollback result with tests proving no partial commit. Do not infer whole-transaction atomicity from one function's local exception block.

### F-07 — Privilege boundary for v2alpha2 helper functions is not accepted

The v2alpha2 verifier declares PL/pgSQL with `SET search_path = pg_catalog` and schema-qualifies fixture objects. It is not declared SECURITY DEFINER; it therefore executes with caller privileges. The audited helper SQL does not establish an explicit production grant/revoke/RLS model for issuer keys, Receipt tables or helper execution. New PostgreSQL functions ordinarily receive PUBLIC EXECUTE unless explicitly revoked.

**Required:** retain invoker semantics unless a separate threat analysis justifies otherwise; add explicit ownership, PUBLIC revocation, EXECUTE grants, table grants and RLS catalog assertions in the disposable security fixture. No production privilege model is approved here.

### F-08 — Action argument contract and handler signature drift

The digest contract defines action-specific fields. The legacy fixture's handler signatures differ: fail takes no business argument, retry and dead-letter take separate parameters, renew takes lease duration, and Complete is a direct multi-statement RLS path rather than a dedicated action function.

**Required:** establish a reviewed binding matrix for every action and make the handler signature, digest schema, Claim identity and SQL mutation use one source of truth.

## 6. Proposed lock and transaction discipline (candidate, not yet implemented)

The final lock order must be proven against all action call paths. Candidate order for Job-mutating actions:

1. Resolve/verify signed Claim and action schema without consuming a durable nonce.
2. Lock exact Tenant/Job row and validate Session, Owner, Epoch, status and DB-clock lease.
3. Lock/check Session row and expected revision where the action requires it.
4. Reserve Receipt using its unique identity and lock/read the existing row on conflict.
5. Insert/validate Nonce Ledger row under its unique key.
6. Apply the Job mutation using the same typed parameters used for Digest recomputation.
7. Insert Transition and Outbox (plus DLQ when applicable).
8. Finalize Receipt with the immutable outcome.
9. Return from the function; caller commits the one transaction.

This order is a design candidate only. Receipt reconciliation and Outbox-only actions may require distinct lock paths. Before adopting it, test deadlock behavior for same Job/same Receipt, same Receipt/different Job, same Operation ID/different key, and concurrent lease/epoch changes.

The invariant is more important than the proposed sequence: every durable write belongs to one transaction; any failure aborts the complete write set; no external broker I/O occurs inside the transaction.
