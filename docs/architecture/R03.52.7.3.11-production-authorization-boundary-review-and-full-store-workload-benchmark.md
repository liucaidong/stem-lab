## 1. Executive determination

The R03.52.7.3.6 reference fixture is reproducibly green, but the current evidence does not close the production authorization boundary.

The most material unresolved issue is the verifier principal's broad internal RLS policies (USING (true) / WITH CHECK (true)). The role is NOLOGIN, NOSUPERUSER, NOBYPASSRLS, non-owner of protected tables, and unavailable to Runtime through SET ROLE. Those are useful controls. They do not prove that every SECURITY DEFINER function owned by the verifier is safe against unintended cross-resource access or unsafe future function additions.

The next engineering objective is to make the verifier's effective authority auditable and resource-constrained while preserving fail-closed behavior. A caller-controlled custom GUC is not a trusted authorization context: Runtime can set custom GUCs. Any replacement relying solely on a GUC, application-supplied tenant ID, caller-writable temporary table, or caller-controlled session variable is rejected.

The reference fixture also does not cryptographically bind the Receipt request digest to the signed assertion. This is a correctness and idempotency boundary, not merely a schema detail.

## 2. Verifier / RLS trust-boundary review

### 2.1 Verified facts

- The verifier role is NOLOGIN, NOSUPERUSER, NOBYPASSRLS and NOINHERIT in the fixture.
- It is not the protected schema or protected table owner.
- Runtime cannot SET ROLE to verifier and cannot directly read issuer keys, nonce ledgers or worker assignments.
- SECURITY DEFINER routines use a fixed search_path and schema-qualified object references; the reference review reports no dynamic SQL in the handlers.
- Selected verifier RLS policies intentionally allow broad internal access to support the SECURITY DEFINER workflow.
- Existing tests exercise cross-tenant/session denial through public operation paths, but do not establish that arbitrary future verifier-owned functions are constrained to the same resource scope.

### 2.2 Threat statement

The relevant threat is not ordinary Runtime directly issuing SELECT against a protected table. That path is already constrained.

The threat is an over-privileged or incorrectly implemented SECURITY DEFINER routine, an unsafe helper call graph, or a future function added under the verifier owner that can use broad internal policies to read or mutate rows outside the intended Tenant/Job/Session/Resource boundary.

The verifier role therefore represents a high-trust database execution boundary. A function allowlist and code review are necessary controls, but they are not equivalent to row-level least privilege.

### 2.3 Options assessed

| Option | Description | Security properties | Cost / limitation | Assessment |
|---|---|---|---|---|
| A. Broad policies + strict function allowlist | Retain broad policies; constrain EXECUTE grants, function ownership, schema CREATE, migration review and catalog audit | Small change; relies on verifier-owned function set remaining correct | A single unsafe function can exercise broad table access; review burden persists | Time-bounded reference posture only; not preferred production target |
| B. Capability-specific NOLOGIN helper roles | Separate verification/read, Job mutation, Claim, DLQ replay and Outbox dispatch authority | Reduces blast radius and makes function-to-table authority explicit | Role/ownership lifecycle complexity; workflows need careful grants | Preferred direction for next design iteration |
| C. Resource-scoped RLS via trusted transaction context | Narrow policies against database-maintained context created only after cryptographic and relationship verification | Can bind row predicates to verified tenant/resource/action/operation | Context lifecycle, transaction binding, nested definer execution and cleanup are nontrivial | Investigate as additional defense; do not implement until integrity is demonstrated |
| D. Verifier BYPASSRLS or table ownership | Bypass RLS for internal routines | Simplifies internal SQL | Removes an independent barrier and increases blast radius | Reject |

### 2.4 Recommended target: B + independently reviewed C

Adopt capability-specific NOLOGIN helper roles as the baseline direction. Each function owner should have only the table/column privileges and RLS policy scope required for its operation family. Keep helper roles NOSUPERUSER, NOBYPASSRLS, NOLOGIN, NOINHERIT and non-owner of protected tables. Runtime, Dispatcher and Replay login principals must not be members of helper roles.

For resource-scoped policies, investigate a database-maintained context whose integrity does not depend on caller-controlled GUCs or caller-writable temporary objects. The context must be transaction-bound and carry at least issuer/key identity, nonce, tenant, job, session, resource type/id, action, operation ID and verified lease fence where applicable. A policy must fail closed if context is absent, stale, ambiguous or not bound to the current transaction.

Do not assume a permanent context table keyed only by backend PID is sufficient: PID reuse, transaction identity, cleanup, aborted transactions, connection pooling and concurrent subtransactions require explicit treatment. Do not assume a custom GUC is trusted merely because a SECURITY DEFINER routine set it earlier; the caller can generally set custom GUC values too. The context mechanism must be demonstrated with adversarial tests before acceptance.

### 2.5 Required evidence

1. Enumerate every SECURITY DEFINER routine, owner, EXECUTE grant, referenced relation, mutation columns and helper call edge.
2. Prove Runtime/Dispatcher/Replay cannot assume helper roles, create/replace helper functions, or alter policy/ownership.
3. Add negative tests invoking every exposed routine with a valid assertion for a different tenant/resource, malformed context, stale context and caller-forged context.
4. Add cross-function confused-deputy tests: a capability valid for one operation must not authorize another helper operation.
5. Add catalog assertions to CI: no unexpected SECURITY DEFINER routine, owner, PUBLIC EXECUTE, helper-role login/BYPASSRLS/table ownership, or dynamic SQL in the reviewed helper set.
6. Preserve cross-tenant/session isolation and rollback atomicity tests.

R535-OD5 remains OPEN until a formal architecture/security owner approves the selected design and evidence.

## 3. Request digest and Receipt idempotency binding

### 3.1 Current gap

The v2alpha1 resource assertion claims do not contain a request digest. The Receipt fixture checks that request_digest is non-empty and constrained, and reconciliation compares stored digests. This does not prove that the digest corresponds to the operation arguments authorized by the assertion.

A client-provided digest is not trusted merely because it is syntactically valid. Comparing a caller-provided digest to a Receipt is insufficient if the trusted handler never recomputes or independently verifies the digest over the normalized operation request.

### 3.2 Compatibility rule

Do not mutate the existing v2alpha1 schema or silently reinterpret its signature semantics. Preserve v2alpha1 as the current experimental fixture contract. Prepare a separate v2alpha2 proposal and explicit migration/compatibility review.

### 3.3 Proposed v2alpha2 contract

Add a required signed claim request_digest to the operation assertion for idempotent state-changing operations.

- Algorithm: SHA-256, fixed by contract version; no caller-selected algorithm.
- Encoding: unpadded base64url of the 32-byte digest.
- Canonical request: RFC 8785 JSON Canonicalization Scheme over a versioned, operation-specific normalized request envelope, or an equally deterministic typed binary encoding approved by review.
- Envelope includes contract version, action, tenant, job, session, resource type/id, operation ID, idempotency key and all semantically relevant operation arguments.
- Exclude transport-only metadata, retry-varying nonce/signature bytes and timestamps not used by business semantics.
- Reject unknown fields and duplicate/ambiguous representations before digest calculation.

The trusted service must canonicalize the request before signing. The database handler must independently derive the digest from the normalized values it will actually apply and compare it to the signed claim before any state mutation. Merely accepting a digest parameter from Runtime does not satisfy this requirement.

The Receipt unique key remains tenant + operation/idempotency identity. A retry must use a fresh assertion and nonce, but preserve the same idempotency identity and request digest. Same identity + same digest returns the existing outcome; same identity + different digest returns a deterministic conflict and performs no mutation.

### 3.4 Required tests

- Valid signature with correct digest and matching normalized operation arguments succeeds.
- Valid signature with mismatching handler arguments fails before mutation.
- Same idempotency key + same digest reconciles to the original Receipt.
- Same idempotency key + different digest conflicts.
- Different JSON property order canonicalizes identically.
- Numeric, Unicode, null/absent, array ordering and duplicate-key edge cases have explicit canonicalization tests.
- Digest mismatch rolls back nonce consumption and all business writes.
- v2alpha1 tokens are not silently accepted as v2alpha2; version dispatch is explicit.

R535-OD3 remains OPEN / PROPOSED until exact canonicalization and signed claim are approved.

## 4. Ambiguous COMMIT fault-injection design

### 4.1 Failure model

A client can lose its connection after sending COMMIT without knowing whether PostgreSQL committed. The client must not blindly replay the state transition with the old assertion/nonce, and must not infer rollback from a transport exception.

### 4.2 Deterministic scenarios

| Scenario | Fault injection point | Expected DB outcome | Client recovery |
|---|---|---|---|
| A. COMMIT not delivered | Drop connection before PostgreSQL receives COMMIT | Transaction rolls back on connection close | Reconcile using fresh assertion; if no Receipt exists, safely execute |
| B. COMMIT accepted, response lost | Forward COMMIT, wait for server completion, then drop response before client receives it | Transaction committed exactly once | Reconcile Receipt using fresh assertion/nonce and same operation ID + digest |
| C. Commit outcome delayed | Hold/blackhole response while independent reconciliation starts | Reconciler may block on unique key/row lock, then observe committed Receipt or proceed after rollback | Bounded retry with DB-clock deadline; no duplicate side effects |
| D. Broken pooled connection | Return faulted connection to pool in deliberately faulty test mode | Pool must detect/discard broken connection; no session state leakage | Reconnect with clean role/GUC state and fresh assertion |

### 4.3 Harness requirements

Use a controllable TCP proxy or test-only protocol fault injector between client driver and PostgreSQL. Expose deterministic barriers for COMMIT observed from client, COMMIT forwarded, server response observed by proxy, and response dropped. Record server-side outcome using a separate privileged observer connection; never use the client exception as the oracle.

Run actual Complete/Fail/Retry and Receipt reconciliation paths, not a synthetic INSERT-only transaction. Assert exactly one Job transition, one Receipt and the expected Outbox event. Verify the old nonce is not reused; reconciliation uses a fresh assertion/nonce but the same operation ID and digest. Race reconciliation against a delayed in-flight transaction and verify unique constraints/locking yield one logical outcome.

Cover both psycopg and node-postgres only if both remain candidate drivers. Keep proxy/fault injection out of production runtime code.

## 5. Outbox delivery and Consumer Dedup integration

The database fixture establishes dispatch lease/epoch fencing and acknowledgement behavior. It does not establish end-to-end delivery semantics or consumer deduplication.

### 5.1 Required consumer contract

- Stable event identity: tenant + event ID, or globally unique event ID with tenant binding.
- Consumer inbox/dedup table with a unique constraint on stable event identity.
- Inbox insertion and consumer business effect occur in one consumer-side transaction.
- Duplicate delivery returns the previously recorded outcome and does not repeat the business effect.
- Payload digest is checked so the same event ID with different payload content is rejected and alerted.
- Acknowledge only after durable consumer acceptance; if ack is lost, redelivery is safe.
- External side effects that cannot share the consumer DB transaction require their own idempotency key/outbox boundary; an inbox alone cannot make an arbitrary remote side effect exactly-once.

### 5.2 Integration matrix

Test normal delivery, consumer commit + ack loss, delivery timeout before consumer commit, duplicate concurrent delivery, same event ID/different payload, expired dispatcher lease/reclaim, stale dispatcher ack, consumer outage/recovery, poison event/DLQ and replay. Measure duplicate suppression and delivery lag. State the guarantee as at-least-once transport + idempotent consumer effect, not exactly-once network delivery.

## 6. Full Store workload benchmark harness

### 6.1 Evidence distinction

The previous CI smoke benchmark is a tenant-scoped single-row RLS read. It is useful as a CI wiring/sanity check only. It must not be used for driver selection, pool sizing, production capacity planning or latency SLO claims.

### 6.2 Workload model

The controlled benchmark must exercise actual authorization and Store transaction paths:

1. Claim with persisted assignment, job-type allowlist, nonce ledger and SKIP LOCKED.
2. Lease renewal with signature verification and owner/epoch/DB-clock fencing.
3. Complete Unit of Work: authorization, Job state transition, Receipt, Transition and Outbox in one transaction.
4. Fail/Retry/Dead-letter, including attempt ceilings and DLQ insertion.
5. Receipt reconciliation under same-digest retry and digest conflict.
6. DLQ Replay with grant/limit checks and fresh Job fencing.
7. Outbox dispatch, lease reclaim, ack, duplicate delivery and consumer inbox dedup.
8. Cross-tenant negative authorization traffic and stale/expired capability traffic.
9. Contention profiles: hot tenant, hot Job, hot nonce/operation key, skewed queue, many tenants and mixed read/write.

Publish a defined reference mix and per-operation isolated measurements. Do not choose production traffic weights without product workload evidence.

### 6.3 Controlled environment requirements

- Pin PostgreSQL major/minor, extension versions, OS image, CPU architecture, kernel, driver and pool versions.
- Declare CPU/memory quotas, storage type/IOPS, network topology/latency, connection limits and PostgreSQL configuration.
- Fix dataset cardinality, tenant distribution, row widths, index definitions, payload sizes and data skew.
- Separate warm-up from measurement; at least five independent measured repetitions per configuration; report variance and confidence intervals.
- Test concurrency and pool sizes as independent variables; do not conflate worker count with connection count.
- Include prepared statement on/off only as a controlled variable.
- Include cold and warm cache profiles; document vacuum/analyze state.
- Capture throughput, p50/p95/p99 latency, error/timeout rate, DB CPU, client CPU, memory, connections, lock waits, deadlocks, WAL volume, buffer/cache hit, transaction duration and queue wait.
- Preserve raw per-run data, configuration manifest, commit SHA, representative SQL plans and reproducible run commands.
- Use identical logical workloads and correctness assertions for every driver candidate.
- A run is invalid if correctness checks fail or resource limits are undeclared.

### 6.4 Candidate comparison

The existing smoke results do not select psycopg3 sync/async, asyncpg or node-postgres. Compare only candidates viable under architecture language/runtime constraints. Keep driver choice OPEN until full Store workloads have been measured on a controlled runner and operational requirements (pool behavior, cancellation, transaction semantics, observability and supportability) have been reviewed.

### 6.5 Required artifacts

- Versioned benchmark workload manifest.
- Dataset generator and deterministic seed.
- Driver adapters implementing identical benchmark operations (not production Store Adapters).
- Correctness oracle and per-run validation report.
- Raw JSON/CSV results and environment manifest.
- Summary report with confidence intervals and no unsupported extrapolation.
- CI smoke job retained separately from controlled benchmark execution.
