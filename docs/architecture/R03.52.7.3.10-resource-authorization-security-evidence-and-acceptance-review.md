## 4. Security evidence established by the fixture

### 4.1 Signature and claim validation

- Ed25519 signature is verified inside PostgreSQL using the pinned pgsodium extension.
- Unknown/revoked key, malformed claims, tampered signature, unsupported action/resource type and invalid time claims fail closed.
- The verifier test asserts acceptance of a valid issued v2 token, not only rejection paths.
- The private signing key is held by the test issuer in the harness and is not persisted in the database keyring.

### 4.2 Tenant, Job, Session and resource binding

- Composite Tenant/Job/Session relationships are exercised.
- Child rows cannot splice another Tenant or Session.
- Job operations require exact persisted Job relationship, owner, epoch, running state and DB-clock lease.
- A stale worker is fenced after owner/epoch reassignment.
- Caller-controlled GUC values alone do not authorize RLS access.

### 4.3 Nonce and transaction replay

- Nonce ledger keys are unique by issuer, key ID and nonce.
- Exact assertion reuse is permitted only inside the same database transaction.
- A committed nonce cannot be reused in another transaction.
- Concurrent duplicate nonce use has one winner.
- Rollback removes nonce consumption together with business writes.
- Claim uses a separate Claim nonce ledger bound to the persisted assignment.

### 4.4 Database principals and privileges

The fixture checks the verifier role is NOLOGIN, NOSUPERUSER, NOBYPASSRLS, non-owner of protected tables/schema, without schema CREATE or table TRUNCATE privilege. Runtime, dispatcher and replay principals cannot assume the verifier role or one another's roles. Runtime cannot directly read issuer keys or nonce/assignment ledgers, cannot mutate Job owner/epoch/lease, and cannot forge Outbox dispatch state or non-Complete Transition/event semantics.

**Important limitation:** the fixture grants the verifier role broad internal RLS policies on selected tables (including `USING(true)` / `WITH CHECK(true)`) so that its SECURITY DEFINER functions can execute the verified internal workflow. The role is non-login and function-owned, but this makes the verifier-owned function set a high-trust database boundary. The production design must decide whether to replace these broad internal policies with resource/transaction-scoped verifier policies, split helper roles, or retain the model with an explicitly reviewed function allowlist and ownership controls. This remains OPEN under the verifier-role/RLS internal-read-path decision; passing tests do not close it.

## 6. Driver/pool benchmark: evidence classification

The CI artifact `store-driver-pool-benchmark-smoke` is a **smoke test**, not a controlled performance benchmark.

Observed environment: GitHub-hosted Linux x86_64 runner, 4 reported logical CPUs, PostgreSQL 17.11, pool bounds 2–16, concurrency 1/8/32, 20 iterations per worker, one repetition, prepared statements disabled.

The benchmark exercises a tenant-scoped RLS-protected single-row read from `tenant_rows` after setting a signed tenant assertion. It does **not** exercise the new Job/Session relationship verifier, nonce ledger, Receipt, Claim, DLQ or Outbox handlers. The run has one repetition and no declared CPU/memory quota, so the numbers are not suitable for driver selection or production capacity planning.

**Do not accept:** the production authorization architecture, production Store Adapter, production driver/pool choice, or production readiness.

1. Obtain explicit approval for R535-OD1 and freeze the action/claim vocabulary.

4. Decide nonce/audit retention and issuer key lifecycle.
5. Add real ambiguous-COMMIT fault injection and external Outbox delivery tests.
6. Run the full Store workload benchmark on a controlled runner.
