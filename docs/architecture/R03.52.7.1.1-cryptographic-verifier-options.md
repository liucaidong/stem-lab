# R03.52.7.1.1 — Cryptographic Verifier Options & Deployment Decision

- Date: 2026-11-02
- Status: technical evaluation; production algorithm/extension NOT_SELECTED
- Related decisions: DEC-03, DEC-14, DEC-19
- R03.52.7.1 HMAC verifier: PASS (reference spike only)
- Product Code Freeze: ACTIVE; P3.17: OUT OF SCOPE

## 1. Executive decision

Do not promote the pgcrypto HMAC spike to the production default.

The preferred cryptographic profile is **Ed25519 asymmetric signature verification**: the issuer retains the private signing key; PostgreSQL receives only the public verification key. This removes the shared signing secret from the database verifier's trust domain.

For self-hosted PostgreSQL or a managed PostgreSQL platform that explicitly supports the extension, **pgsodium is the leading database-side verifier candidate** because it exposes libsodium's `crypto_sign_verify_detached(sig, message, public_key)` SQL function.

However, pgsodium is not a universal PostgreSQL capability. The final choice is gated by DEC-14 deployment/provider selection and a support/lifecycle review. If the target managed service does not support pgsodium or another vetted asymmetric verifier, evaluate a dedicated trusted DB access gateway that exclusively owns the database credentials; do not silently fall back to HMAC or caller-controlled GUC.

## 2. Verified implementation facts

### PostgreSQL pgcrypto

Official PostgreSQL documentation describes:
- `hmac(data, key, type)` as a keyed MAC: both issuer and verifier need the same secret.
- PGP public-key functions as encryption/decryption functions.
- PGP implementation limitation: no support for signing.

Therefore pgcrypto alone does not provide the asymmetric detached-signature verification required by the preferred design. The R03.52.7.1 HMAC function remains useful as a working trust-boundary reference, not as the default production crypto profile.

Sources:
- https://www.postgresql.org/docs/current/pgcrypto.htm

### pgsodium / libsodium

The pgsodium PostgreSQL extension exposes:
- `crypto_sign_detached(message, secret_key)`
- `crypto_sign_verify_detached(signature, message, public_key)`
- `crypto_sign_new_keypair()`

The verify function accepts the public key and returns a boolean. The signing private key need not be placed in PostgreSQL. Libsodium's `crypto_sign` API is Ed25519.

Verified installation constraints from the project documentation:
- pgsodium requires libsodium >= 1.0.18.
- pgsodium 3.x requires PostgreSQL 14+.
- It is a native PostgreSQL extension requiring installation on the database host/image; it is not a pure SQL-only dependency.
- The extension must be installed in the `pgsodium` schema and functions should be schema-qualified to reduce search_path-hijacking risk.
- Server Key Management / `shared_preload_libraries` is optional. It is not required merely to verify signatures with a public key; it is relevant when using server-managed secret keys.
- PGXN lists 3.1.11 as the latest stable release, dated 2026-06-10.

Sources:
- https://github.com/michelp/pgsodium
- https://www.pgxn.org/dist/pgsodium/
- https://doc.libsodium.org/public-key_cryptography/public-key_signatures

### Managed PostgreSQL compatibility caveat

- Supabase currently labels pgsodium as pending deprecation and says it does not recommend its use on the Supabase platform.
- A search of the currently published official extension catalogs for Amazon RDS PostgreSQL, Google Cloud SQL for PostgreSQL and Azure Database for PostgreSQL Flexible Server did not find pgsodium. This is a support-catalog observation, not a claim that every provider/version has identical rules; re-check the exact target service and major version before selecting it.

Sources:
- https://supabase.com/docs/guides/database/extensions/pgsodium
- https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html
- https://docs.cloud.google.com/sql/docs/postgres/extensions
- https://learn.microsoft.com/en-us/azure/postgresql/extensions/how-to-create-extensions

## 3. Option comparison

| Option | Trust/key model | Strengths | Costs / risks | Current disposition |
|---|---|---|---|---|
| A. pgcrypto HMAC in SECURITY DEFINER | Issuer and DB verifier share secret | Available in stock PostgreSQL; already has passing reference spike | Shared-secret blast radius; DB verifier can forge if its secret boundary is compromised; key custody/rotation/replay still needed | Reference fallback only; not production default |
| B. pgsodium Ed25519 in RLS path | Issuer holds private key; DB holds public key | Asymmetric trust separation; direct DB-side verification; exact RLS integration | Native extension packaging, upgrade/security review, managed-provider availability and operational support | Preferred DB-side candidate, subject to deployment gate |
| C. Reviewed custom PostgreSQL C extension | Issuer holds private key; DB holds public key | Full control of algorithm/API and DB-side execution | We own C code, ABI/build matrix, memory safety, signing library upgrades and supply-chain review | Only if B unavailable and gateway unacceptable |
| D. Dedicated trusted DB access gateway | Gateway verifies Ed25519; gateway exclusively holds DB credentials; app/worker cannot connect directly | Portable across managed PostgreSQL providers; no custom DB extension | Adds network/service hop, availability and latency; DB credential and network isolation must be enforceable; app must have no direct SQL path | Mandatory fallback candidate for providers without B |
| E. Per-tenant DB role/credential or isolated DB | Database authenticates distinct tenant identity | Stronger isolation tier; limits shared-RLS blast radius | Role/pool/credential cardinality and operations cost | High-assurance tier (DEC-19 C) |

## 4. Gateway fallback is valid only under strict conditions

A gateway is not a security boundary if the ordinary API/Worker still has a direct database credential.

For Option D to qualify:
1. Only the gateway has network reachability and credentials to the tenant data database.
2. API and Worker identities cannot open arbitrary SQL connections to that database.
3. Gateway authenticates the calling workload and verifies the signed assertion independently; client-supplied tenant selectors are not trusted.
4. Gateway exposes typed, bounded data operations rather than a generic SQL passthrough.
5. Gateway starts a transaction, installs transaction-local context, executes the approved operation, and clears context on commit/rollback.
6. RLS remains enabled and forced as defense in depth; runtime database identity is gateway-only and least privilege.
7. Gateway compromise is treated as a data-plane compromise and is addressed by isolation, deployment identity, audit, rate limits, and incident controls.

If any application workload retains direct DB access, caller-controlled GUC is still spoofable and this gateway model is rejected.

## 5. Recommendation

1. **Preferred:** run an Ed25519 verifier inside PostgreSQL using pgsodium when the chosen database deployment supports and operationally approves it.
2. **Fallback:** for managed providers without a supported asymmetric verifier extension, use a dedicated DB access gateway with exclusive database credentials and network-enforced isolation. Keep the database RLS layer, but treat the gateway—not a GUC—as the authenticated trust boundary.
3. **Do not select:** pgcrypto HMAC as the general production default. Keep the current HMAC spike as evidence that the RLS integration and privilege model can work.
4. **Do not build a custom C extension** until B and D are evaluated against the selected provider and operational constraints.
5. DEC-14 must identify deployment topology/provider before the final verifier implementation is selected. DEC-03 still controls the production Worker/API runtime and must not be inferred from the Python test harness.

## 7. Non-decisions

- No production cryptographic algorithm, extension, gateway, provider, deployment topology or key-management service is selected by this document.
- The HMAC test fixture key is ephemeral and must never be reused in any environment.
- No production-ready or production tenant-isolation claim is made.
