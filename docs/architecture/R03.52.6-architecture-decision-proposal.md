## DEC-19 — Trusted Tenant Context

**Problem.** Transaction-local PostgreSQL GUC is caller-controlled state. Existing RLS policy filters rows according to the GUC but does not authenticate the tenant identity. The PostgreSQL adversarial harness intentionally demonstrates that a SQL-capable application role can change the GUC and read another tenant's row.

**Approved target.** Retain application authorization (verified principal + server-side tenant membership + action/resource policy) as the first layer. Persist the resolved tenant on the Job. A separate trusted issuer signs a short-lived assertion bound to subject, tenant, audience, action, resource/job, expiry and nonce. The database—not merely the API process—must verify assertion authenticity, scope and expiry through a narrowly privileged verifier before RLS accepts the tenant context. RLS policies must validate the signed assertion (or a transaction context cryptographically derived from it), not trust a caller-set tenant GUC. Prefer asymmetric signatures with the verification key unavailable for mutation by the runtime role; if the chosen database crypto profile requires a protected symmetric key, it must be inaccessible to the runtime role and callable only through a hardened verifier. The verifier must not disclose key material or offer a tenant-selection bypass. Worker Store operations additionally fence persisted tenant/job/owner/epoch/DB-clock expiry. Plain GUC-only authorization is rejected.

**Alternatives.** A (application predicates only) is insufficient as sole control at scale; C (database role/credential per tenant) offers stronger identity separation but increases pool/credential/role cardinality. See the isolation-options document.

**Consequences.** More issuer/verifier and key-management complexity; every DB entry point must bind context to a transaction; issuer/verifier outage denies access. Residual compromise of issuer or privileged DB identities remains in scope.

**Production enablement gates (still OPEN).** Threat-model/security-owner sign-off; issuer isolation and key custody; database-side verifier prototype and adversarial proof that the runtime role cannot forge, replace, bypass or widen a tenant assertion; missing/spoof/expiry/replay/tenant/action/audience/resource mismatch tests; transaction/pool commit/rollback/cancellation/reset tests; Worker cross-tenant claim/renew/complete/fail fencing; SECURITY DEFINER, role/grant and privileged-path review; verifier performance/failure benchmark; operational key rotation/revocation and incident procedure; named security/operations approval.

**Decision: ACCEPTED (target architecture only).** Default shared-tenant target is B + mandatory A-layer authorization and tenant-aware SQL predicates. C (tenant-specific DB identity/credential or isolated DB) remains an approved escalation option for high-assurance tenants. Production enablement remains BLOCKED until every gate above is closed. The Python HMAC verifier is a reference contract, not production trust establishment.

## DEC-04 — Production Store / Pool / Migration

**Problem.** Current PostgreSQL scripts are disposable integration harnesses. No production Store adapter, pool, migration lifecycle, or connection budget exists.

**Approved target.** Define a language-neutral Store protocol and explicit Unit of Work. Use short bounded transactions for claim/renew/complete/fail/replay; never hold DB connections during handler execution. Separate least-privilege runtime, migration and audited administrative identities. Adopt expand/contract migrations, immutable checksummed artifacts, migration locking, forward-fix/compensating migration and restore tests. Bound pool size, acquisition queue and timeouts; discard uncertain connections. Keep Worker fencing and transaction atomicity as invariants.

**Candidates to benchmark.** psycopg 3 + psycopg_pool; asyncpg + pool; SQLAlchemy 2.x async engine/pool. PostgreSQL 17 remains CI test target only. Python production runtime is not selected (DEC-03 OPEN).

**Implementation/technology gates (still OPEN).** Production runtime selection under DEC-03; PostgreSQL major-version/support policy; driver/pool benchmark; cancellation and connection-reset proof; pool exhaustion and failover tests; transaction/retry/error contract; migration interruption/restore/compatibility tests; multi-process Worker tests; observability/capacity review; named implementation approval.

**Decision: ACCEPTED (architecture principles only).** No driver, pool or migration tool is selected. Concrete implementation remains gated on DEC-03 and the evidence above.
