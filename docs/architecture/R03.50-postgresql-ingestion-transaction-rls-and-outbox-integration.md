# R03.50 PostgreSQL Ingestion Transaction, RLS & Outbox Integration

- Date: 2026-11-02

- Risks: AUD-001, AUD-003, AUD-004

## 1. Objective

Validate the Package Ingestion lifecycle's critical persistence transaction on a real PostgreSQL service:
- idempotency receipt reservation;
- row-locked optimistic state transition;
- append-only transition ledger;
- durable Outbox event;
- atomic commit/rollback;
- tenant-scoped RLS;
- concurrent stale-revision race behavior.

This is a disposable integration-test schema, not a production migration or ingestion service.

## 2. Transaction boundary

One transition command executes as one database transaction:
1. reserve (tenant, session, operation, idempotency_key) with request_digest;
2. if the key already exists, return the prior receipt when digest matches, otherwise reject conflict;
3. SELECT session FOR UPDATE;
4. compare expected_revision and validate the state edge;
5. update session status and revision;
6. append immutable transition record;
7. insert Outbox event;
8. store the deterministic command receipt;
9. commit.

Any failure rolls back the receipt reservation, state update, transition row and Outbox event together.

## 3. Persistence constraints

- Composite primary key (tenant_id, session_id) for sessions.
- Transition rows reference sessions with a composite tenant-aware foreign key.
- Unique tenant/session/command_id and tenant/session/idempotency_key.
- Transition sequence is unique per tenant/session.
- Outbox event ID and per-session sequence are unique.
- Transition ledger rejects UPDATE and DELETE via a database trigger.
- Receipt stores request digest and response; same key/same digest is replay, same key/different digest is conflict.

## 4. Tenant isolation

The harness creates a NOLOGIN, NOSUPERUSER, NOBYPASSRLS app role, applies ENABLE/FORCE ROW LEVEL SECURITY and a transaction-local app.tenant_id policy to sessions, transitions, receipts and Outbox.

Important limitation: this GUC is set by the application role and is not an independent security boundary against arbitrary SQL execution or compromised app credentials. It is defense-in-depth only. DEC-19 remains OPEN.

## 5. CI test coverage

- atomic transition + receipt + Outbox commit;
- same-key/same-digest replay without duplicate transition;
- same-key/different-digest conflict;
- stale revision rollback without receipt;
- injected Outbox failure rolls back all writes;
- tenant RLS isolation;
- append-only transition ledger;
- two concurrent commands with same expected revision yield exactly one winner.

## 6. Not implemented

No production DDL migration, connection pool, authenticated API, trusted tenant-context issuer, broker relay, Worker lease/fencing, retry scheduler, quarantine storage, signature/license verification or operational monitoring is implemented.

The Outbox event is persisted only; no real broker publish or consumer is exercised. The test role and schema are disposable CI artifacts.

## 7. Exit criteria

R03.50 fixture scope is complete when all PostgreSQL tests pass against the CI PostgreSQL service and failures/limitations are documented. This does not close AUD-001/AUD-003/AUD-004 or DEC-04/19/30.


## 8. CI evidence — Run #212

GitHub Actions [Run #212](https://github.com/liucaidong/stem-lab/actions/runs/41430210617) completed SUCCESS. The PostgreSQL harness ran 8 tests and passed:
- atomic session transition + receipt + Outbox commit;
- same idempotency key and digest replay;
- same key with a different digest conflict;
- stale revision rollback without a receipt;
- injected Outbox failure rolls back session, transition and receipt;
- tenant RLS isolation;
- append-only transition ledger;
- concurrent same-revision commands produce exactly one winner and one stale-revision conflict.

Runs #208/#210 exposed a real lock-ordering defect: reserving an idempotency receipt before locking the parent session caused FK KEY SHARE and SELECT FOR UPDATE lock-upgrade deadlocks under concurrent commands. The transaction order was corrected: fast-path receipt lookup, lock session, recheck receipt, validate revision, then insert receipt and write state/transition/Outbox. Run #211 then exposed a schema-qualified test query defect; it was corrected before Run #212. Failed runs remain visible.

The harness proves the behavior of this disposable PostgreSQL schema and app role only. Tenant GUC is still not a security boundary against arbitrary SQL under compromised app credentials; no production migration or Broker relay is included.
