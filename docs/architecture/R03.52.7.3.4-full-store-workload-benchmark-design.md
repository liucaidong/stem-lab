# R03.52.7.3.4 — Full Store Workload Benchmark Design

- Date: 2026-11-02
- Status: design proposal; implementation NOT_STARTED
- Related: R03.52.7.2 Store Protocol, R03.51 concurrency model, DEC-03, DEC-14, DEC-19
- Product Code Freeze: ACTIVE; P3.17: OUT OF SCOPE

## 1. Purpose and non-goals

The current benchmark proves that candidate drivers can execute a short tenant-scoped PostgreSQL transaction through Ed25519 verification and RLS. It does not yet measure the Store's actual transactional work.

This design defines the next benchmark fixture and operation mix. It is a disposable benchmark schema and conformance harness, not a production Store adapter or production migration. It must not be used to claim production readiness.

## 2. Workload boundary

Every candidate must run the same logical SQL operation sequence and the same correctness assertions. Driver-specific adapters may differ in API style but may not:
- omit SQL statements, locks, constraints, RLS checks or transaction boundaries;
- replace DB-clock fencing with client-clock decisions;
- weaken tenant/resource authorization;
- use a different isolation level or schema/index set;
- perform business computation or network I/O inside the transaction;
- retry an operation whose commit outcome is unknown without reconciliation.

A Unit of Work is one checked-out connection, one verified tenant assertion context and one bounded transaction.

## 3. Disposable benchmark schema

The fixture should include the minimum relational shape needed to exercise the accepted Store contract:

| Table | Required columns / constraints | Purpose |
|---|---|---|
| `bench_sessions` | tenant_id, session_id, revision, state JSONB; PK (tenant_id, session_id) | Revision fencing and session mutation |
| `bench_jobs` | tenant_id, job_id, session_id, job_type, status, priority, payload, attempt_count, maximum_attempts, available_at, lease_owner, lease_expires_at, lease_epoch, completed_at; composite FK to Session | Claim, lease, retry and completion |
| `bench_receipts` | tenant_id, session_id, job_id, idempotency_key, request_digest, result_ref; unique (tenant_id, session_id, idempotency_key) | Idempotent completion record |
| `bench_transitions` | tenant_id, session_id, job_id, from_status, to_status, lease_epoch, created_at | Immutable state-transition history |
| `bench_outbox` | tenant_id, session_id, job_id, event_id, payload, created_at, published_at; unique event_id within tenant | Atomic durable event publication |
| `bench_dlq` | tenant_id, job_id, terminal_reason, error_code, attempt_count, lease_epoch | Dead-letter terminal state |
| `bench_worker_assignments` | tenant_id, worker_id, job_type, enabled | Persisted worker-to-tenant/job authorization |

All tenant-bearing tables require ENABLE + FORCE ROW LEVEL SECURITY and tenant-aware composite keys/foreign keys. All tables are owned by a migration/verifier identity; runtime roles are non-owner, NOSUPERUSER, NOBYPASSRLS and have only the minimum DML grants.

The fixture must use the database-side signed assertion verifier. The legacy `app.tenant_id`-only policy in older reference SQL is not acceptable for this benchmark.

## 4. Assertion and resource binding

The existing verifier accepts expected tenant, audience, action and resource. The benchmark must use that exact database-side check; a GUC alone is never identity proof.

Proposed action/resource mapping to validate before implementation:

| Operation | Assertion action | Resource binding | Additional DB predicate |
|---|---|---|---|
| Claim | `claim` | worker_id (bound as expected resource; subject/assignment semantics must be verified) | persisted worker assignment and supported job types |
| Renew | `renew` | job_id | persisted tenant, owner, epoch, running status, lease expiry |
| Complete | `complete` | job_id | persisted tenant, owner, epoch, unexpired lease, expected Session revision |
| Fail | `fail` | job_id | persisted tenant, owner, epoch, unexpired lease |

**Contract gap to resolve:** the v1alpha1 `JobLease` does not carry the persisted Session ID, while completion touches both Job and Session. The design must prove resource-scoped RLS on Session/Receipt/Transition/Outbox without widening authorization to every row in the tenant. Candidate approaches:
1. include Session scope in a versioned assertion/lease contract and enforce it in RLS;
2. use a hardened database-side relationship verifier that validates the signed job resource and proves the target Session is the Session persisted on that Job;
3. use distinct signed resource assertions within one UoW, only if the protocol is explicitly versioned to support multiple assertions.

Do not silently choose a tenant-wide policy or rely only on adapter SQL predicates. This is a security design gate, not a benchmark tuning parameter.

The current verifier does not persist/consume assertion nonces. Replay semantics must be decided and tested before claiming one-time assertion behavior. At minimum, the benchmark must verify the accepted short-lived assertion semantics and ensure the same assertion cannot cross tenant/action/resource boundaries. If nonce consumption is adopted, it must be atomic with the operation transaction and idempotent replay behavior must be explicit.

## 5. Operation definitions

### 5.1 Claim

- Begin transaction and establish trusted tenant assertion context.
- Select one eligible queued/retry job or expired running lease using stable order and `FOR UPDATE SKIP LOCKED`.
- Validate persisted worker assignment and supported job type.
- Update owner, DB-clock expiry, attempt count and monotonically increasing epoch.
- Commit before returning the lease.
- A no-work result commits/ends promptly and does not hold a connection while polling.

### 5.2 Renew

- Update only a running Job whose tenant, job ID, owner and epoch match and whose lease has not expired according to `clock_timestamp()`.
- Return STALE/EXPIRED for zero-row update.
- No stale owner may renew after reclaim increments epoch.

### 5.3 Complete

One atomic transaction, preserving the accepted lock order:
1. lock Job and verify tenant/owner/epoch/expiry;
2. lock Session and check expected revision;
3. update Session revision/state;
4. insert deterministic idempotency Receipt;
5. append immutable Transition;
6. insert Outbox event;
7. update Job to succeeded and clear lease;
8. commit.

Inject failure after each write boundary and prove all-or-nothing rollback. Duplicate idempotency key with the same digest returns the prior outcome; same key with a different digest returns IDEMPOTENCY_CONFLICT.

### 5.4 Fail / retry / DLQ

- Verify the active unexpired owner/epoch fence.
- Retryable error below max attempts updates retry state and available_at using DB time, clears lease and appends the appropriate transition.
- Non-retryable error or exhausted attempts updates dead_lettered state and inserts DLQ record atomically.
- Duplicate fail command is idempotent; stale epoch cannot change terminal state.

## 6. Workload profiles

Do not invent a single production traffic mix. Benchmark isolated operation profiles first, then allow a declared configurable composite mix.

Required profiles:
- claim-heavy queue contention;
- renew-heavy long-running work;
- completion-heavy transactional write path;
- fail/retry/DLQ-heavy failure path;
- balanced multi-tenant queue;
- hot-tenant skew and mixed-tenant fairness.

The composite mix must be recorded as explicit percentages in the result manifest and sum to 100%. The same seeded dataset and operation mix must be used for every driver.

## 7. Correctness gates before performance

A run is invalid if any invariant fails:
- no cross-tenant read/write;
- no forged, tampered, expired, wrong-audience, wrong-action or wrong-resource assertion accepted;
- no stale owner/epoch renews, completes or fails;
- no lease expiry decision uses client clock;
- no Session revision lost update;
- no duplicate Receipt/Transition/Outbox side effect;
- no same idempotency key with a different digest silently accepted;
- no partial completion state after injected rollback;
- no cross-tenant foreign key/reference;
- no tenant assertion state leaked across pooled connection reuse;
- no handler work while a DB transaction/connection is held;
- no unclassified ambiguous commit.

Correctness tests must run independently of the timing loop. A fast but incorrect driver is disqualified.

## 8. Metrics and fault matrix

Per operation and per driver:
- successful operations/sec, p50/p95/p99 latency and error rate by StoreErrorCode;
- pool acquire wait and queue depth;
- active/idle/waiting connections and connection churn;
- DB CPU, memory, lock waits, deadlocks, transaction age, WAL volume and I/O timing;
- tenant distribution/fairness and queue starvation;
- assertion verification overhead;
- connection discard/reset rate and cancellation completion time.

Faults:
- cancellation before statement, during statement, during COMMIT and during pool release;
- network reset before/during/after COMMIT;
- PostgreSQL restart/failover;
- pool exhaustion and acquisition timeout;
- worker process death after Claim commit;
- old worker completion after reclaim;
- retry and DLQ commit interruption;
- outbox insert failure;
- duplicate completion and ambiguous commit reconciliation.

## 9. Candidate execution order

Once the schema and assertion resource scope are accepted:
1. Psycopg 3 sync + psycopg_pool;
2. Psycopg 3 async + AsyncConnectionPool;
3. asyncpg + Pool;
4. node-postgres + pg-pool.

This is only the test order. The order may be changed if DEC-03 selects a different runtime first. SQLAlchemy and postgres.js remain optional challengers, not default requirements.

## 10. Exit criteria

R03.52.7.3.4 can be marked PASS only when:
- the benchmark-only DDL and RLS policies are reviewed against the current tenant trust model;
- the assertion resource-scope gap is resolved without weakening RLS;
- all four driver adapters execute identical operation semantics;
- correctness and adversarial tests pass;
- controlled runs have at least five repetitions and an approved environment manifest;
- fault matrix is exercised and results are reproducible;
- raw results and exact environment/dependency manifests are retained.

Until then: full Store workload benchmark NOT_IMPLEMENTED; production driver/pool NOT_SELECTED; production_ready remains false.
