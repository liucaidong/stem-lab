## 1. 设计目标与非目标

目标：
- 将R03.14逻辑实体映射到可审阅的PostgreSQL schema/table候选；
- 用tenant-scoped unique key与composite foreign key减少跨租户错误关联；
- 明确Runtime命令、Receipt、Event、Outbox的事务原子性；
- 明确RLS覆盖、后台任务和连接池上下文要求；
- 为后续DB/RLS Spike提供可执行测试清单。

非目标：
- 本文不是生产DDL、迁移脚本或ORM Schema；
- 不代表PostgreSQL版本、Drizzle/迁移工具或云服务已选定；
- 不代表RLS已实现或通过安全测试；
- 不冻结分区、索引、软删除或数值列精度。

## 3. 主键与租户作用域

### 3.1 ID策略

- 候选主键：UUID；UUIDv7与ULID仍需在DEC/ADR中比较索引局部性、生成位置、隐私和生态兼容。
- 不把可猜测的顺序ID当作授权凭据。
- 公开API使用不透明资源ID；是否与数据库主键相同需安全评审。
- 任何租户业务实体都应有tenant_id，或通过不可绕过的复合外键关系继承归属。

### 3.2 Composite key约束模式

对tenant-owned实体，建议同时建立：
- 主键 `id`；
- 唯一约束 `UNIQUE (tenant_id, id)`；
- 子表使用 `FOREIGN KEY (tenant_id, parent_id) REFERENCES parent(tenant_id, id)`。

该模式使跨租户parent引用在数据库约束层失败，而不只依赖应用查询条件。跨租户共享内容必须通过独立的Global Catalog/授权映射表达，不允许简单省略tenant过滤。

Command事务：Session锁定→租户/权限校验→幂等键与request_hash检查→expected_state_version检查→更新Session/State→写Receipt/Event/Outbox→提交。任一步失败全部回滚。

Result Commit事务：校验execution/session/epoch/lease/fencing/input_state_version→校验结果Schema与digest→写Observation/Execution/State/Event/Outbox→提交。大文件上传在事务外完成；事务内只引用已验证对象，失败对象进入孤儿清理流程。

## 5. RLS设计候选

### 5.1 基本策略

每张tenant-owned表：
- ENABLE ROW LEVEL SECURITY；
- FORCE ROW LEVEL SECURITY（需评估owner、迁移和后台角色行为）；
- SELECT/UPDATE/DELETE使用tenant predicate；
- INSERT/UPDATE的WITH CHECK验证新行tenant_id；
- 通过composite FK限制跨租户关联；
- 资源级授权（课程成员、Assignment、教师角色）由应用Policy层执行，必要时以受控函数/策略补强。

事务上下文候选：认证中间件在每个数据库事务开始时写入transaction-local tenant context；事务结束后自动清理。不得依赖连接级永久SET，避免连接池复用泄漏。

### 5.2 安全限制

PostgreSQL自定义GUC可被具备相应数据库权限的会话设置，因此基于GUC的RLS上下文主要是防止应用漏加过滤条件的纵深防御，不是抵御已被攻陷的应用数据库凭证的唯一边界。必须同时做到：
- 数据库凭证不下发浏览器/客户端；
- 使用参数化SQL，禁止不可信输入拼接SQL；
- 应用角色最小权限，禁止绕过RLS的BYPASSRLS；
- 明确表Owner、迁移角色、后台服务角色和只读角色；
- 对跨租户后台任务使用独立角色、明确授权和审计；
- 对安全敏感环境评估每租户角色、隔离数据库或可信签名上下文等更强隔离方案。

### 5.3 RLS测试矩阵

| ID | 场景 | 预期 |
|---|---|---|
| RLS-01 | Tenant A读取Tenant B主键 | 无数据可见，不泄露存在性 |
| RLS-02 | Tenant A写入tenant_id=B | WITH CHECK拒绝 |
| RLS-03 | Tenant A引用Tenant B的session/course | Composite FK或Policy拒绝 |
| RLS-04 | 连接池事务结束后复用连接 | 不继承上个租户上下文 |
| RLS-05 | 缺少tenant context | 默认拒绝，不回退到全表可见 |
| RLS-06 | 普通应用角色尝试绕过RLS | 权限拒绝 |
| RLS-07 | 后台跨租户任务 | 仅专用角色可执行，必须审计 |
| RLS-08 | UPDATE修改tenant_id | 拒绝或由不可变约束阻止 |
| RLS-09 | 软删除/归档查询 | 不跨租户泄露已归档记录 |
| RLS-10 | Object Storage签名URL | 资源归属和授权通过后才签发 |

## 6. 时间、数值与分区候选

- 业务时间统一使用timestamptz并按UTC语义存储；simulation_time独立于wall clock。
- 事件和Observation需要稳定序号/唯一tie-breaker，不能依赖数据库默认返回顺序。
- 科学标量暂列double precision与numeric两种候选；必须依据Solver数值语义、序列化精度、查询需求和成本Spike决定，不在此冻结。
- 大型时序/波形/图像放Object Storage，数据库保存digest、size、schema、授权和索引元数据。
- Events/Observations按时间或tenant分区可能有价值，但必须先有真实数据量和查询基准；早期不默认分区。
- 不以物理删除替代RetentionPolicy；数据库、对象存储、缓存、导出和备份需统一生命周期。

## 7. 迁移与发布顺序候选

1. 建立identity与tenant membership；
2. 建立content不可变版本与asset元数据；
3. 建立learning组织、Assignment和Package Lock；
4. 建立runtime session/command/receipt/event/outbox；
5. 建立execution/lease/fencing；
6. 建立science observation/dataset/snapshot；
7. 建立governance audit/retention/deletion；
8. 逐阶段启用RLS并运行跨租户回归；
9. 通过迁移回滚、备份恢复和并发事务Spike后才允许生产发布。

此顺序只是依赖候选；真实迁移工具、在线迁移策略、数据回填和停机窗口仍未确定。
