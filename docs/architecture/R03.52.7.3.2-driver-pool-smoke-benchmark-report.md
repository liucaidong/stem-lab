## 1. Scope and evidence level

This run proves that the benchmark adapters can execute a tenant-scoped PostgreSQL transaction through the database-side Ed25519 assertion verifier and RLS using:
- Psycopg 3 synchronous API + psycopg_pool;
- Psycopg 3 asynchronous API + AsyncConnectionPool;
- asyncpg + its pool;
- node-postgres (`pg`) + pg-pool.

PostgreSQL 17.11 and the pgsodium Ed25519 verifier fixture were used. Each measured operation:
1. acquires a pooled connection;
2. begins a transaction (explicitly for asyncpg and node-postgres; via Psycopg connection transaction context for Psycopg);
3. applies the runtime role locally;
4. installs a signed tenant assertion transaction-locally;
5. performs a tenant-filtered RLS-protected row read;
6. commits and returns the connection to the pool.

Pool min/max: 2/16. Prepared statement caches were disabled for a portable baseline. Concurrency levels: 1, 8, 32. Measured iterations per worker: 20.

**Evidence classification:** CI functional/smoke evidence only. GitHub-hosted runner CPU, memory, network, virtualization noise and contention are not controlled. The workload is a simple RLS read, not the full Claim/Renew/Complete/Fail transactional workload. No performance SLO or production driver selection can be derived from this run.

## 3. Interpretation (strictly preliminary)

- node-postgres + pg-pool produced the highest throughput in this one CI smoke run at concurrency 8 and 32. This is a signal to prioritize deeper TypeScript API benchmarking, not evidence that Node is intrinsically faster or that pg-pool is selected.
- asyncpg and Psycopg async were close at concurrency 8/32; asyncpg showed lower p95 at concurrency 8, while Psycopg async showed lower p95 at concurrency 32. The sample is too small and uncontrolled to rank them.
- Psycopg sync had the strongest single-concurrency result in this run. It remains a viable synchronous Worker baseline.
- Pool acquisition wait becomes material at concurrency 32 for all Python candidates. The benchmark's pool max is 16, so queueing is expected; the next iteration must expose connection occupancy and waiter depth.
- No candidate has yet been tested with transaction-pooler mode, database failover, cancellation during COMMIT, connection loss, ambiguous commit reconciliation, context-leak adversarial cases, or complete business transaction mix.
