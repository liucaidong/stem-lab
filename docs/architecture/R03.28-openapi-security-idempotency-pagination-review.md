## 1. 范围与判定

本审阅只覆盖当前四个OpenAPI操作：创建Session、读取Session、提交Runtime Command、分页读取Observation。

OpenAPI 0.2已通过OpenAPI 3.1规范验证（Run #41/#42）。本轮OpenAPI 0.3候选已补充Observation value_ref.size_bytes与simulation_time非负约束，并扩展API静态语义断言；Run #49已通过，详见[Contract validation #49](https://github.com/liucaidong/stem-lab/actions/runs/41392793514)。这证明文档符合规范结构，不证明JWT校验、资源授权、幂等存储、游标一致性或限流在服务端已实现。

## 3. 必须补充的安全与授权约束

### 3.1 JWT验证边界

API Gateway/Auth Middleware必须验证：
- 签名与允许算法白名单；拒绝`none`及算法混淆；
- issuer、audience、exp、nbf、必要时iat；
- key id、密钥轮换、撤销和JWKS缓存失效策略；
- subject与内部User映射；tenant membership状态；
- 角色/权限不能仅由客户端请求字段决定。

JWT仅完成认证，不自动授予任意资源访问权。每个Session/Assignment/Observation读取或变更都必须执行资源级授权。

### 3.2 Tenant与资源隔离

- Tenant ID必须来自可信认证上下文，不能从query/body/header中接受客户端自声明作为授权依据。
- 每个资源查询先验证tenant归属，再验证课程/班级/Assignment成员关系及角色。
- 不可见资源统一返回404还是403需形成全API一致策略；当前Session读取/Observation读取使用404隐藏资源存在性，是合理候选。
- RLS是纵深防御，不替代应用层资源授权；后台任务须使用独立最小权限身份。
- 资源ID不可预测不等于授权。

### 3.3 Request Body边界

`CreateSessionRequest.client_context`当前允许任意属性（`additionalProperties: true`），仅通过description要求“不包含敏感信息”。Schema无法强制该描述。

建议在下一版将client_context改为明确allow-list字段，并设置`additionalProperties: false`；字段由产品/客户端架构共同确定，不在本审阅中擅自定义。禁止把Token、邮箱、真实姓名、学校/班级标识、精确定位或未成年人敏感信息放入自由扩展字段。

`RuntimeCommandRequest.payload`当前是通用object。必须在服务端按`command_type + schema_version`路由到版本化Command Payload Schema；未知类型/版本拒绝，不可将任意对象直接交给Worker执行。

## 4. 幂等与并发语义

当前要求：
- CreateSession和SubmitRuntimeCommand均必须携带Idempotency-Key；
- Command必须携带If-Match，代表客户端观察到的expected state version；
- 同一tenant、资源/操作作用域、Idempotency-Key、相同canonical request hash：返回原Receipt，不重复副作用；
- 相同key但不同request hash：409 Conflict；
- If-Match版本不匹配：409 Conflict，并在安全允许时返回current_version；
- Receipt、状态变更、Domain Event、Outbox必须处于同一数据库事务。

仍需ADR明确：
1. Idempotency-Key作用域（tenant + endpoint + resource）；
2. 保存期限、清理策略和超期重试语义；
3. request canonicalization/hash算法与字段排序/默认值规则；
4. 并发相同key请求的唯一约束、等待/冲突策略；
5. key冲突与state version冲突的稳定Error Code；
6. ETag采用强验证器还是弱验证器，以及If-Match语法/比较规则。

不得只在API进程内存中实现幂等；必须使用持久化唯一约束与事务语义。

## 5. Cursor Pagination语义

当前`limit`边界1–500，`cursor`不透明；但“stable cursor-paginated page”尚缺少可测试定义。

建议下一版契约固定：
- 排序键：由服务端定义稳定的复合顺序，至少有唯一tie-breaker；不能依赖数据库自然顺序。
- Snapshot/high-water mark：第一页确定查询边界，后续页保持相同逻辑快照，避免新增Observation导致跨页重复或遗漏。
- Cursor内容绑定tenant_id、session_id、排序规则、过滤条件、last key和snapshot watermark。
- Cursor应完整性保护（签名/MAC或服务端存储随机句柄），不可由客户端伪造或修改。
- Cursor需设定有效期；过期时返回稳定错误码，并说明是否要求从第一页重启。
- limit是否可在同一游标链中变化必须明确；建议固定在cursor内，或者拒绝变化。
- 返回next_cursor为null代表无后续页；空items与null cursor的组合语义需明确。

**待决策：** Observation是否增加服务端单调sequence字段作为稳定tie-breaker，需与R03.14/R03.27数据模型同步；本审阅不假设该字段已经存在。

## 6. 错误模型与HTTP状态

建议统一：
- 400：JSON/YAML等请求结构错误、字段格式错误；
- 401：凭证缺失、过期、签名或issuer/audience验证失败；
- 403：已认证但明确拒绝授权（仅在不泄露资源存在性时使用）；
- 404：资源不存在或对当前主体不可见；
- 409：If-Match版本冲突、幂等键复用冲突、状态迁移冲突；
- 422：结构合法但违反领域/科学约束；
- 429：限流/租户配额，提供Retry-After；
- 500：不泄露堆栈、内部路径、SQL、Token或内部服务信息。

Error Code应稳定、机器可读；message供人理解，不作为程序分支条件。每个错误必须包含correlation_id。field_errors不得回显用户输入中的敏感值。
