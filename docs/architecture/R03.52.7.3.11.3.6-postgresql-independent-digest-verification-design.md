# R03.52.7.3.11.3.6 — PostgreSQL Independent Digest Verification Design

**Status:** DESIGN ONLY / IMPLEMENTATION NOT COMPLETE / FAIL-CLOSED GATE

## 1. Required trust boundary

PostgreSQL must not accept the Runtime's request_digest or canonical bytes as authoritative. The database must derive envelope identity fields from the verified Assertion Claim and construct operation_arguments from the exact typed parameters used by the same SQL handler.

The digest comparison must occur before any durable nonce, Receipt, Job, Transition, DLQ or Outbox change. If the handler has already created transactional writes, any later failure must abort/rollback the entire outer transaction.

## 2. Required database API shape

Each action handler should pass its own typed arguments to a private digest helper. The helper must not accept an arbitrary caller-provided JSON envelope as proof. Examples:

- renew: verified Claim + lease_seconds integer
- complete: verified Claim + expected_session_revision bigint + result_ref text
- fail: verified Claim + error_code text + safe_message text + retryable boolean + retry_delay_micros bigint
- retry: verified Claim + delay_seconds integer + error_code text
- dead_letter: verified Claim + error_code text + terminal_reason text

No handler may use a second, unbound argument after digest comparison. The same local typed variables must be used both to construct the digest input and to execute the SQL mutation.

## 3. Canonical byte construction

Implement the candidate typed encoding using PostgreSQL bytea:
- fixed domain separator bytes;
- fixed field order;
- convert_to(text, 'UTF8') for strings;
- int4send for unsigned 32-bit network-order lengths after range validation;
- recursive typed value encoder for the constrained operation argument object;
- bytea concatenation only after size/depth/count checks;
- SHA-256 from a verified, pinned database function.

Do not hash jsonb::text. Do not rely on jsonb object iteration order without an explicit byte-order contract. Do not cast floating point or unconstrained numeric values.

## 4. Duplicate-key handling

PostgreSQL jsonb discards duplicate object keys. Therefore raw signed Claim JSON must be decoded to PostgreSQL json first, recursively inspected with json_each/json_array_elements for duplicate object keys, and only then cast to jsonb. The trusted signer must also reject duplicate keys before signing. The DB duplicate-key check is defense in depth and prevents parser disagreement.

Operation arguments should preferably be constructed from typed SQL parameters rather than accepted as raw arbitrary JSON. If raw JSON is ever accepted, duplicate-key validation must occur before jsonb conversion.

## 5. Digest comparison and nonce semantics

- Verify signature and semantic Claim constraints.
- Recompute digest using actual operation parameters.
- Compare exact lowercase sha256:hex string against signed Claim request_digest.
- On mismatch, raise a deterministic authorization/digest error and ensure no nonce ledger row persists.
- On a successful operation, nonce insert, Receipt arbitration, business transition and event writes share the same outer transaction.
- If an operation returns false/null after an exception, the Unit of Work must rollback; it must never commit based only on a falsey return value.

## 6. Why this is not yet implemented

The current fixture uses pgsodium for Ed25519 but the exact SHA-256 primitive and extension/version contract for this branch have not yet been proven from the pinned PostgreSQL image. The current handler set also has mixed argument surfaces (SECURITY DEFINER writes versus Runtime RLS Unit-of-Work writes). Adding an unverified SQL digest helper now would risk hashing a representation different from the values actually executed.

This design therefore remains a hard implementation gate. No production or database-independent digest verification claim is made.
