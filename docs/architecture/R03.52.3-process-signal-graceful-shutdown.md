# R03.52.3 Process Signal & Graceful Shutdown Bridge

- Date: 2026-11-02
- Status: Executable Python reference + unit tests; CI pending
- Parent: R03.52.1 / R03.52.2
- Product Code Freeze: ACTIVE
- P3.17: OUT OF SCOPE / MUST NOT ENTER
- Related decisions: DEC-03, DEC-13, DEC-14

## 1. Objective

Bridge OS termination signals to the existing WorkerPool shutdown contract. Signal callbacks must remain minimal and must not access PostgreSQL, mutate Job state, block on joins, or perform handler work.

## 2. Signal handling model

1. Install SIGINT/SIGTERM handlers from the process main thread only.
2. A handler only sets an in-memory Event.
3. A dedicated monitor thread observes the Event and calls WorkerPool.request_shutdown().
4. WorkerPool fans shutdown out to each WorkerRuntime.
5. WorkerRuntime stops new claims and allows active handlers to drain while lease heartbeat continues.
6. On exit, restore the previously installed signal handlers.

The signal bridge does not release leases or mark jobs complete. If the process is forcibly terminated, R03.51 lease expiry/reclaim/fencing remains the recovery mechanism.

## 3. Executable reference

- runtime/process_lifecycle.py: SignalShutdownBridge and run_with_signal_handling().
- scripts/test_process_lifecycle.py: signal forwarding, handler restoration, main-thread restriction and invalid configuration tests.
- Tests patch the signal API and use a fake Pool; no real process termination is sent in CI.

## 4. Shutdown deadline and deployment boundary

This module does not enforce a hard shutdown deadline. A non-cooperative handler can keep the pool alive. Deployment must configure a termination grace period based on maximum handler duration and lease policy, then allow the orchestrator to force-kill the process if the deadline expires. Forced termination must not issue a synthetic success or lease release; leases expire naturally.

DEC-14 deployment topology remains OPEN. Python is still a reference implementation only; DEC-03 remains OPEN.

## 5. Explicit limitations

- No container/orchestrator lifecycle hook or restart/backoff policy.
- No hard cancellation of running Python threads.
- No health/readiness endpoint or metrics exporter.
- No PostgreSQL Store adapter or tenant-context trust boundary.
- No distributed scheduler or broker relay.
- Signal handling can only be installed from the main thread.
- This code is not evidence of production process supervision.

## 6. Verification

Required tests:
- SIGTERM forwards shutdown through the monitor thread;
- previous signal handlers are restored;
- installation from a non-main thread is rejected;
- empty signal list and invalid monitor interval are rejected.

Passing tests prove the signal bridge reference only, not deployment behavior.
