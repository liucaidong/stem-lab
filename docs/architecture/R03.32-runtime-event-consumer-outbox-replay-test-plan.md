# R03.32 Runtime Event消费语义、Outbox与重放测试计划

- 版本：0.1；日期：2026-11-02
- 状态：协议与测试计划；未执行NATS/Outbox/Consumer集成Spike
- 关联：R03.7、R03.10、R03.15、R03.18、R03.20 DEC-05/DEC-30、R03.26

## 1. 设计目标

Runtime Event用于投影、分析、通知和异步流程，不应成为Session权威状态的第二写入口。权威状态仍由Command Handler事务更新。Event消费者必须假设消息可能重复、延迟、重放或在跨分区/跨聚合场景下乱序。

本计划不承诺端到端Exactly-Once。目标是At-Least-Once Delivery + Durable Inbox/Idempotency + Per-Aggregate Sequence Guard，使可重试投递不会造成重复业务副作用。

## 2. Producer / Transactional Outbox

Command Handler事务候选：
1. 校验Tenant/Actor/权限、Session stateVersion和Idempotency-Key；
2. 更新权威Session/Execution/Observation记录；
3. 写Command Receipt；
4. 写Domain Event（event_id、aggregate_id、aggregate_sequence、event_type、schema_version、payload_digest）；
5. 写Outbox Message；
6. 同一数据库事务提交。

Outbox Relay：
- 仅读取已提交的Outbox记录；
- 发布时携带稳定event_id和aggregate_sequence；
- Broker确认后标记published_at；未确认则可重试；
- 进程在“Broker已接收但数据库未标记published”窗口崩溃时，允许重复发布；
- Outbox保留/清理必须晚于消费者重放和审计窗口。

因此消费者必须具备持久化幂等处理；不能依赖Relay内存状态或Broker消息ID作为唯一去重边界。

## 3. Consumer Inbox与顺序控制

每个Consumer维护：
- inbox：consumer_name + event_id唯一；
- payload_digest：检测同event_id不同内容；
- aggregate cursor：consumer_name + aggregate_type + aggregate_id + last_processed_sequence；
- processed_at、schema_version、result status；
- retry_count和failure classification。

建议事务：
1. 收到事件，验证Envelope/Payload Schema；
2. 尝试插入Inbox唯一键；
3. 若event_id已处理且digest相同，作为Duplicate Ack，不重复执行副作用；
4. 若event_id相同但digest不同，进入安全/完整性异常，不覆盖旧记录；
5. 比较aggregate_sequence：
   - 等于last_sequence+1：允许处理；
   - 小于等于last_sequence：重复/迟到事件，按事件身份和历史记录判定；
   - 大于last_sequence+1：存在gap，不推进cursor，进入等待/重试/隔离策略；
6. 在同一事务中更新Consumer Projection、Inbox和aggregate cursor；
7. 提交成功后Ack Broker。

若消费者需要触发外部副作用（邮件、Webhook、第三方API），必须使用自己的Outbox或外部幂等Key，不得在Projection事务提交前直接执行不可回滚副作用。

## 4. Event Envelope不变量

- event_id全局唯一且不可变；
- aggregate_sequence在同一aggregate内严格递增，不要求跨aggregate全局有序；
- 同一个aggregate_sequence只能对应一个event_id；
- event_type与schema_version必须在Registry中存在；
- payload_digest应覆盖规范化Payload，算法/规范化规则需登记；
- occurred_at是业务事件时间，不作为排序或去重主键；
- correlation_id和causation_id用于因果追踪，不代替event_id；
- Tenant ID来自可信Producer上下文，Consumer不得相信payload内的任意租户声明；
- 不同事件类型的Payload Schema必须独立版本化。

## 5. Duplicate / Out-of-Order / Replay测试矩阵

| ID | 测试 | 预期 |
|---|---|---|
| EVT-C01 | 同event_id、同payload重复投递 | 第二次无重复副作用，Ack |
| EVT-C02 | 同event_id、不同payload_digest | Integrity Alert，拒绝覆盖 |
| EVT-C03 | 同aggregate_sequence、不同event_id | Producer/Consumer冲突，拒绝 |
| EVT-C04 | sequence连续递增 | 正常处理并推进cursor |
| EVT-C05 | sequence出现gap | 不推进cursor；进入可观测重试/隔离流程 |
| EVT-C06 | 旧sequence迟到 | 不回滚Projection |
| EVT-C07 | 两个aggregate事件交错 | 每个aggregate独立顺序正确 |
| EVT-C08 | Consumer在Projection写入前崩溃 | 未Ack，Broker重投后正常处理 |
| EVT-C09 | Projection提交后、Ack前崩溃 | 重投被Inbox去重 |
| EVT-C10 | Outbox发布成功、published标记前崩溃 | 允许重复发布，Consumer不重复副作用 |
| EVT-C11 | Broker暂时不可用 | Outbox保留并重试，不丢事件 |
| EVT-C12 | Schema未知版本 | 隔离/兼容失败，不静默丢弃 |
| EVT-C13 | Consumer从指定sequence重放 | Projection可确定性重建 |
| EVT-C14 | Replay触发外部通知 | 不重复发送或使用Replay专用副作用策略 |
| EVT-C15 | poison event持续失败 | 有界重试、DLQ/隔离、告警和人工处理 |
| EVT-C16 | Tenant A订阅Tenant B事件 | 授权拒绝且不泄露数据 |
| EVT-C17 | event_id重复但Tenant不同 | Integrity/Security Alert |
| EVT-C18 | Inbox保留期清理后历史重放 | 必须由Replay/Retention策略明确，不能意外重复副作用 |

## 6. Replay与Schema演进

- Projection重建应使用隔离的Consumer identity或rebuild namespace；
- Replay必须记录起始sequence、结束sequence、snapshot digest、schema/upcaster版本和执行者；
- 旧Schema事件应通过明确upcaster或对应Consumer版本处理，不允许猜测性字段转换；
- Replay默认关闭通知/外部副作用，或使用稳定副作用ID去重；
- DLQ消息应保留event_id、aggregate、schema_version、payload_digest和失败分类；敏感payload需加密/最小化访问；
- 重放完成后必须对Projection数量、序列游标和关键聚合不变量做对账。

## 7. 当前契约缺口

1. R03.26仅覆盖SessionStarted、ExecutionSucceeded、ObservationRecorded三种Payload；
2. Event Envelope Schema尚需确认aggregate_sequence、payload_digest、causation_id等字段的正式名称/必需性；
3. 当前Registry和Fixture测试尚未实现Inbox、Outbox、Broker Ack和Consumer cursor；
4. DEC-05 NATS JetStream仍为PROPOSED，尚未执行Broker参数和故障Spike；
5. Delivery semantics和sequence gap策略尚未由架构负责人批准。

## 8. WBS与退出条件

- W2.3保持IN PROGRESS：补齐Event类型、Envelope字段和Schema版本策略；
- W3.2保持NOT STARTED：Outbox与Broker重复/乱序/重放Spike；
- 必须执行EVT-C01–C18中适用测试，并附CI/集成环境日志；
- 需覆盖Producer提交后崩溃、Relay重复发布、Consumer提交后Ack前崩溃；
- 必须证明Tenant隔离和Replay不会重复外部副作用；
- 未通过前不得宣称Event Pipeline可靠或可生产运行。

## 9. 结论

建议采用At-Least-Once + Durable Inbox/Outbox + Per-Aggregate Sequence Guard作为待验证候选，而不是宣称Exactly-Once。当前只有部分Event Schema和静态Fixture验证，尚无真实Broker/DB/Consumer故障测试。W2.3/W3.2继续未关闭。
