# R03.52.7.2 — Store Protocol & Unit of Work Contract

- Date: 2026-11-02
- Status: PASS (driver-neutral contract); production adapter NOT_IMPLEMENTED
- Related: DEC-03, DEC-04, DEC-13, DEC-19, DEC-30
- Product Code Freeze: ACTIVE; P3.17: OUT OF SCOPE
- Production Store adapter: NOT_IMPLEMENTED

## 1. Objective

Define the stable, driver-neutral persistence boundary consumed by API command handlers and Worker orchestration before choosing a PostgreSQL driver, pool, runtime or migration tool.

Artifacts:
- Machine-readable request/response schema: `contracts/worker-store-protocol.schema.v1alpha1.json`
- Python reference types and protocols: `runtime/store_protocol.py`
- Contract tests: `scripts/test_store_protocol_contract.py`

These artifacts define semantics and types only. They do not implement SQL, connection acquisition, migrations, event transport or production persistence.

## 2. Trust and tenant scope

- A Store operation receives an opaque `StoreAccessContext` containing a signed assertion and audience.
- The protocol deliberately has no caller-supplied top-level `tenant_id` selector.
- The assertion binds the tenant and operation scope; the trusted verifier derives the effective tenant context.
- One Unit of Work is bound to one verified tenant context. Cross-tenant work uses separate access contexts and separate transactions.
- Persisted Job tenant is authoritative. If a payload contains `tenant_id`, it must equal the persisted Job tenant; payload identity is never used to choose the RLS context.
- Claim authorization is derived from the worker's trusted assignment/scope, not from a list of arbitrary tenant IDs supplied in the claim command.

## 3. Store and Unit of Work

Logical interface:

```text
Store.begin(access_context, timeout_seconds) -> UnitOfWork

UnitOfWork.claim(ClaimRequest) -> ClaimedJob | None
UnitOfWork.renew(JobLease, lease_seconds) -> StoreOutcome
UnitOfWork.complete(CompleteJobCommand) -> StoreOutcome
UnitOfWork.fail(FailJobCommand) -> StoreOutcome
UnitOfWork.commit() -> None
UnitOfWork.rollback() -> None
```

A Unit of Work:
- represents exactly one bounded database transaction and one tenant context;
- is single-use and must not be shared across threads/tasks;
- acquires a connection only for the transaction;
- commits explicitly or rolls back on exception/cancellation;
- is never retained while a handler performs scientific computation, file processing or external I/O;
- rejects operations after commit/rollback;
- installs verified context transaction-locally and relies on the selected verifier/RLS path;
- does not expose a generic SQL passthrough to application/Worker callers.

The Python `Protocol` is a reference expression of the language-neutral contract. A future TypeScript, Python sync or Python async adapter must preserve the same semantics.

## 4. Operation semantics

### 4.1 Claim

- Claim request contains worker ID, supported job types, bounded lease duration and `max_items=1` in v1alpha1.
- Tenant scope comes from the trusted assertion, not the request body.
- In one short transaction, select an eligible row using stable ordering and `FOR UPDATE SKIP LOCKED`, update owner/expiry, increment attempt count and monotonically increment lease epoch.
- Database clock is authoritative for availability and expiry.
- Commit before returning the job to the Worker Runtime.
- No row returns `None`; do not hold locks or a connection while waiting for work.

### 4.2 Renew

- Predicate must include persisted tenant, job ID, running status, owner, epoch and `lease_expires_at > clock_timestamp()`.
- A zero-row update returns STALE/EXPIRED; it must never silently renew a stale lease.
- A successful renewal extends expiry using database time.
- The runtime stops side effects after renewal failure or lease-loss signal.

### 4.3 Complete

One transaction must:
1. lock the Job and validate tenant/job/owner/epoch/unexpired lease;
2. enforce idempotency key + canonical request digest;
3. lock the Session and compare expected revision;
4. update Session;
5. insert immutable completion Receipt;
6. append Transition;
7. insert the required Outbox event(s);
8. mark Job succeeded and clear lease;
9. commit all changes atomically.

A duplicate with the same idempotency key and digest returns DUPLICATE. Reuse of the same key with a different digest returns IDEMPOTENCY_CONFLICT. A stale or expired lease produces no Session, Receipt, Transition or Outbox writes.

### 4.4 Fail / retry / DLQ

- Failure writes are fenced by tenant/job/owner/epoch/DB clock.
- Persist stable error code and redacted safe message only; never persist raw exception text, credentials, archive contents or signed URLs.
- Retry decision and delay are supplied by the retry policy layer; Store persists `available_at` and returns immediately. Workers never sleep while holding a lease.
- Permanent failure or exhausted attempts transitions to DLQ atomically with the required audit/outbox records.
- External event delivery remains governed by DEC-30; Store guarantees only the database transaction/outbox write boundary.

## 5. Outcomes and error taxonomy

Mutation outcomes: `APPLIED`, `DUPLICATE`, `STALE`, `EXPIRED`, `RETRY_SCHEDULED`, `DEAD_LETTERED`.

Stable errors:
- TENANT_ACCESS_DENIED
- JOB_NOT_FOUND
- LEASE_STALE / LEASE_EXPIRED
- SESSION_REVISION_CONFLICT
- IDEMPOTENCY_CONFLICT
- POOL_ACQUIRE_TIMEOUT
- TRANSIENT_DATABASE_FAILURE / PERMANENT_DATABASE_FAILURE
- TRANSACTION_OUTCOME_UNKNOWN
- SCHEMA_VERSION_UNSUPPORTED
- INVARIANT_VIOLATION

Driver exceptions must be translated into stable codes and safe messages. Raw SQL text and driver messages are not part of the public contract.

### Ambiguous commit

If the connection is lost during COMMIT and the adapter cannot determine whether the transaction committed:
- return TRANSACTION_OUTCOME_UNKNOWN with `outcome_known=false`;
- do not transparently retry the mutation;
- discard the connection;
- reconcile by the operation idempotency key/receipt on a fresh transaction;
- if reconciliation is unavailable, surface unknown outcome to the caller.

This prevents duplicate side effects after an ambiguous commit.

## 6. Pool and connection ownership

The Store adapter owns connection acquisition/release. Contract requirements:
- bounded pool size and acquisition queue;
- explicit acquisition, statement and transaction deadlines;
- connection reset/validation on checkout and checkin;
- rollback on exception and cancellation;
- discard connections with uncertain protocol/transaction state;
- context cannot leak across transactions or pool reuse;
- no connection retained during handler execution;
- pool exhaustion is backpressure and returns POOL_ACQUIRE_TIMEOUT, not unbounded connection creation.

Concrete pool settings and library remain OPEN pending DEC-03 runtime and load benchmark.

## 7. Migration boundary

- Runtime identity has no DDL privileges.
- Migration runner uses a separate identity and immutable checksummed artifacts.
- Expand/contract, migration lock, bounded backfill, interruption/retry, restore and forward-fix are migration contract requirements.
- Store protocol does not invoke migrations at process startup.

## 8. Compatibility and versioning

- Schema version is explicit (`1alpha1`).
- Unknown operation/version or additional unrecognized fields are rejected.
- Additive optional fields may be introduced only under a versioned compatibility policy; semantic changes require a new version.
- Idempotency keys are scoped to tenant + operation; request digest uses canonical serialization.
- Store errors and outcomes are stable API concepts, not driver exception aliases.

## 9. Verification

The contract test suite must verify:
- schema is valid Draft 2020-12 JSON Schema;
- claim/renew/complete/fail request fixtures validate;
- arbitrary top-level tenant selector and claim batching are rejected in v1alpha1;
- access context is opaque;
- Job payload tenant mismatch is rejected;
- lease epoch/timezone invariants hold;
- idempotency digest and safe error message bounds hold;
- unknown commit outcome is explicit.

CI status is recorded in the verification report. These tests validate contract shape and reference invariants only; they do not prove a production Store adapter.

## 10. Non-decisions and next gates

Not selected: PostgreSQL major version for production, driver, pool, sync/async runtime, migration framework, query builder, PgBouncer mode, deployment topology or event bus. DEC-03 and DEC-14 remain OPEN; DEC-04 architecture principles are ACCEPTED.

Next increment: build a conformance harness that runs the same Store contract against an in-memory reference model and then a PostgreSQL adapter only after runtime/driver gates are approved. Do not implement the production adapter merely to satisfy this contract stage.
