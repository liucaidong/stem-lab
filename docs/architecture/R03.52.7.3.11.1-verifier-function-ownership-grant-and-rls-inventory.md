# R03.52.7.3.11.1 — Verifier Function, Ownership, Grant and RLS Inventory

**Status:** SOURCE_REVIEW / REFERENCE_FIXTURE_ONLY / PRODUCTION_NOT_READY  
**Source:** scripts/test_postgres_resource_scoped_authorization.py at PR #13 reference branch  
**Source blob:** 9b120be277485673514ed890edb1c57a61eecaad  
**Purpose:** Establish a concrete function and policy inventory before changing verifier ownership or RLS semantics. This inventory describes the disposable fixture, not a production database catalog snapshot.

## 1. Executive finding

The fixture defines 11 SECURITY DEFINER functions in the generated resource-auth schema. All 11 are explicitly transferred to the same NOLOGIN verifier role and PUBLIC EXECUTE is revoked. Nine functions are directly granted to Runtime, Dispatcher or Replay login roles; two functions are private nested helpers.

This is a materially concentrated trust boundary: a single verifier role owns cryptographic verification, authorization, Job state transitions, Claim, DLQ replay, Outbox dispatch/ack and the RLS predicate helper. The broad verifier policies apply to this shared owner identity, not to individual function identities.

The inventory confirms the reason to investigate capability-specific helper roles. It does not, by itself, prove an exploitable vulnerability in the current fixed function set. The tested public paths enforce resource predicates. The residual concern is blast radius and future/incorrect definer code under the same broad owner authority.

## 3. Ownership and call graph

All functions share one owner: the verifier role.

Observed principal call paths:

- Runtime → authorize_v2 → verify_v2 → issuer_keys + pgsodium signature verifier + Job/Session or Receipt checks + nonce_ledger.
- Runtime → renew_v2/fail_v2/retry_v2/dead_letter_v2 → verify_v2 → authorize_v2 → nonce_ledger → protected state tables / Transition / Outbox / DLQ.
- Runtime → claim_next_v1 → Claim assertion verification → issuer_keys + worker_assignments + claim_nonce_ledger + queue Job rows.
- Runtime RLS policy → assertion_allows → nonce_ledger, bound to pg_current_xact_id().
- Dispatcher → dispatch_outbox_v2 / ack_outbox_v2 → verify_v2 + outbox_dispatchers + Outbox + nonce_ledger.
- Replay → replay_dlq_v2 → verify_v2 + dlq_replay_principals + DLQ + Job + nonce_ledger.

The source defines no separate function owner for Claim, Dispatcher, Replay or RLS predicate evaluation. All paths converge on the same verifier owner.

These policies are not directly assigned to Runtime, Dispatcher or Replay. Their practical reach is through SECURITY DEFINER functions executing as the common verifier owner. Because that owner is shared, policy scope cannot distinguish which verifier-owned function is currently executing.

The fixture's Runtime policies are separate and use assertion_allows(...) to bind rows to a nonce-ledger entry for the current transaction. This is a stronger row-scope predicate for direct Runtime Unit-of-Work writes, but it does not narrow the verifier role's own internal policies.

## 5. Verifier table privilege inventory

The source grants the verifier role:

- SELECT on issuer_keys.
- SELECT on sessions, jobs, receipts, dlq_items and dlq_replay_principals.
- INSERT on jobs.
- UPDATE(replay_count) on dlq_items.
- UPDATE(status, lease_expires_at, owner, available_at, attempt_count, last_error_code, epoch) on jobs.
- SELECT, INSERT on nonce_ledger.
- SELECT on worker_assignments and outbox_dispatchers.
- SELECT plus column-limited UPDATE on Outbox dispatch state/owner/epoch/lease/attempts/dispatched_at.
- SELECT, INSERT, UPDATE on claim_nonce_ledger.
- INSERT on transitions, outbox and dlq_items.
- USAGE and CREATE on the generated schema during setup; the test later asserts verifier has no schema CREATE privilege after function setup/role hardening.

The pgsodium signature verification function is granted to verifier. Runtime has column-limited Job update (status only), scoped SELECT, Receipt/Transition insert/select, and constrained Outbox insert. Runtime cannot directly update owner/epoch/lease.

## 6. Findings and risk assessment

### F-01 — Single shared definer owner

**Evidence:** all 11 functions transfer ownership to the same verifier role.  
**Impact:** every function inherits the same table privileges and verifier RLS policy reach.  
**Assessment:** high-trust concentration; blast-radius concern. Not proof of a presently exploitable path.

### F-02 — Broad verifier policies

**Evidence:** 17 verifier policies use unconditional true predicates across protected relations.  
**Impact:** resource isolation inside the verifier boundary is enforced by handler predicates and function correctness rather than the verifier's own RLS policies.  
**Assessment:** primary R535-OD5 issue; production least-privilege closure absent.

### F-03 — Runtime RLS predicate helper is SECURITY DEFINER

**Evidence:** assertion_allows is owned by verifier, granted to Runtime and called from Runtime policies; it checks current transaction ID and exact nonce-ledger row fields.  
**Impact:** Runtime policy evaluation depends on this trusted helper. Its implementation is compact and scoped, but its owner has the same broad verifier role authority.  
**Assessment:** preserve the current transaction-binding semantics; consider moving this helper to a dedicated read-only authorization-check role with only SELECT on nonce_ledger, rather than granting it the general operation-helper owner.

### F-04 — Claim uses same verifier owner despite separate contract

**Evidence:** claim_next_v1 independently parses and validates Claim assignment capability, but is owned by the same verifier role and uses broad policies.  
**Impact:** Claim-specific trust boundary is not isolated from Job mutation, DLQ and Outbox helper code.  
**Assessment:** candidate for a dedicated Claim helper role.

### F-05 — Dispatcher and Replay are separately authenticated, not separately owned

**Evidence:** distinct login principals and function grants exist, but their SECURITY DEFINER handlers share verifier ownership.  
**Impact:** direct entry grants are separated, while internal database authority is not.  
**Assessment:** candidate for dedicated Outbox and Replay helper roles.

## 7. Recommended capability-role decomposition

This is a design proposal, not an approved change.

| Proposed NOLOGIN role | Functions | Minimum table authority to derive and verify |
|---|---|---|
| auth_assertion_reader | verify_v2; possibly assertion_allows under a separate narrowly scoped predicate owner | issuer_keys SELECT; pgsodium verify EXECUTE; nonce_ledger SELECT for predicate helper only |
| auth_job_mutator | authorize_v2, renew_v2, fail_v2, retry_v2, dead_letter_v2 | Job/Session/Receipt reads; nonce insert/select; Job allowed mutation columns; Transition/Outbox/DLQ inserts |
| auth_claim | claim_next_v1 | issuer key read + signature verify; assignment read; Claim nonce read/insert/update; queue Job select/insert/update only required columns |
| auth_outbox | dispatch_outbox_v2, ack_outbox_v2 | dispatcher assignment read; event-scoped Outbox read/update; nonce read/insert |
| auth_dlq_replay | replay_dlq_v2 | replay grant read; DLQ read/update replay_count; Job insert/read; nonce read/insert; Transition/Outbox insert if required by implementation |
| auth_rls_predicate | assertion_allows | nonce_ledger SELECT only; no mutation or unrelated relation grants |

A helper role may own only its own SECURITY DEFINER functions. No role should be a member of another helper role unless a narrowly documented dependency requires it. Prefer small invoker-safe helpers or explicit grants over role inheritance. Every helper role remains NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOINHERIT and non-owner of protected tables. PUBLIC EXECUTE remains revoked.

This matrix is a starting point: derive exact table/column privileges from every SQL statement in each function body before implementation. Do not copy this matrix mechanically.

## 8. Required implementation and test gates

1. Produce a machine-readable manifest of function identity, signature, owner role, SECURITY DEFINER flag, search_path, EXECUTE grantees, referenced relations and mutations.
2. Add CI catalog assertions comparing actual pg_proc/pg_roles/pg_class/pg_policy/ACL state against the manifest.
3. Split owners in a disposable branch only; do not change the existing PR #13 reference implementation in place.
4. For each helper role, prove that unrelated operation tables are inaccessible even when a function body is deliberately modified in a negative test.
5. Test direct SET ROLE, inherited role membership, PUBLIC EXECUTE, schema CREATE, function replacement and search_path shadowing attacks.
6. Test cross-tenant, cross-session, cross-resource and cross-action confused-deputy attempts through every public function.
7. Test rollback, concurrent nonce duplicate, transaction-local context and pool reuse.
8. Preserve all existing 46 tests; new least-privilege tests must be additive.

## 9. Conclusion

The concrete inventory confirms a single verifier owner across 11 SECURITY DEFINER functions and 17 broad internal RLS policies. The current reference fixture has useful perimeter controls and operation-level predicates, but its internal least-privilege boundary is not sufficiently decomposed for production acceptance.

**Recommendation:** proceed with a disposable capability-role split experiment and catalog-based tests. Do not modify production contracts, close R535-OD5, alter PR #13, or claim that the split is approved until the experiment demonstrates least privilege without weakening the existing operation invariants.
