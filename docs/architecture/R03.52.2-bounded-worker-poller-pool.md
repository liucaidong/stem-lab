# R03.52.2 Bounded Worker Poller Pool & Concurrency Supervision

- Date: 2026-11-02
- Status: Executable process-local reference + unit tests; CI pending
- Parent: R03.52.1
- Product Code Freeze: ACTIVE
- P3.17: OUT OF SCOPE / MUST NOT ENTER
- Related decisions: ADR-001, ADR-005, DEC-03, DEC-04, DEC-05, DEC-13, DEC-19, DEC-30

## 1. Objective

Run a fixed, explicitly bounded number of R03.52.1 WorkerRuntime pollers inside one process. Each poller has a distinct stable worker identity and independently claims durable work through the Store abstraction.

This is not a distributed Scheduler. Durable ordering/claiming remains in the PostgreSQL Job claim transaction. The pool only supervises local concurrency and propagates unexpected poller termination.

## 2. Invariants

1. Configured concurrency is a positive integer and is the maximum number of poller loops created.
2. Each poller has a unique worker_id; duplicate identities fail startup.
3. Every poller shares the injected Store/handler configuration only through the factory; connection-pool thread safety remains the Store adapter's responsibility.
4. Shutdown fans out to all pollers, preventing future claims and allowing active handlers to drain under R03.52.1 semantics.
5. Unexpected poller exit or exception stops the whole pool and propagates the failure to the process entrypoint.
6. No automatic restart loop is embedded in the pool; restart/backoff belongs to a future process supervisor and must avoid restart storms.
7. No dynamic scaling, per-tenant fairness, weighted quotas or global concurrency coordination is implemented.

## 3. Scheduling boundary

The PostgreSQL claim operation remains the durable scheduler:
- available_at and database clock determine due work;
- priority and deterministic tie-breakers order candidates;
- FOR UPDATE SKIP LOCKED prevents duplicate concurrent claims;
- lease expiry and epoch fencing recover crashed workers.

The in-process pool does not hold Job rows while handlers run and does not make process-local memory authoritative.

## 4. Executable reference

- runtime/worker_pool.py: fixed-size poller supervisor.
- scripts/test_worker_pool.py: bounded concurrency, unique identity, shutdown fan-out and failure propagation tests.
- CI uses fake poller runtimes; no PostgreSQL Store adapter or external process supervisor is included.

## 5. Operational failure model

| Failure | Expected behavior |
|---|---|
| Poller idle | Its WorkerRuntime waits for the configured poll interval |
| Shutdown requested | Pool requests shutdown on every runtime |
| Active handler | Runtime continues heartbeat and drains cooperatively |
| Poller raises | Pool requests shutdown on peers and propagates the exception |
| Poller exits unexpectedly | Pool treats it as a process-level failure |
| Process hard-killed | Leases expire and R03.51 reclaim/fencing applies |

The pool deliberately does not restart individual pollers. A future supervisor may restart the process only after classifying the failure and applying bounded exponential backoff/jitter.

## 6. Explicit limitations

- No DB adapter, transaction pool, connection budget or trusted tenant context.
- No per-tenant fairness or noisy-neighbor isolation.
- No deployment-level CPU/memory limits, process health checks or OS signal integration.
- No hard timeout for non-cooperative handlers; the orchestrator must enforce a termination grace externally.
- No cross-process/global concurrency cap. Multiple replicas multiply configured concurrency.
- No Broker relay, DLQ replay, or telemetry exporter.
- DEC-03/04/05/13/19/30 remain OPEN.

## 7. Verification

Required unit tests:
- exactly N pollers start and all drain;
- duplicate worker identity rejected;
- invalid concurrency/monitor interval rejected;
- shutdown before start creates no worker threads;
- unexpected poller failure stops peers and propagates.

Passing tests verify local orchestration only. They do not establish production Scheduler or Worker readiness.
