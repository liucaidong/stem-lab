# R03.12 部署拓扑、质量工程与发布验证计划

- 版本：0.1；日期：2026-11-02
- 状态：部署与验证基线草案；需容量Spike和运行演练
- 关联：R02.5发布门禁、R03、R03.6 TF-11/12

## 1. 部署原则

首期采用Modular Monolith + Independent Scientific Worker。先控制分布式系统复杂度；只有在独立扩展、隔离、团队边界或可靠性有明确收益时才拆分服务。开发环境可容器化；生产部署平台、云厂商和区域待目标市场与数据驻留决策后冻结。

## 2. 逻辑部署单元

- Web Client：静态资源/CDN，浏览器运行；
- API/BFF：无状态应用实例，认证、授权和应用用例；
- PostgreSQL：权威事务状态、索引和元数据；
- Outbox Publisher：发布已提交事件；
- NATS JetStream：持久化异步消息；
- Scheduler：Execution调度、lease和fencing；
- Scientific Worker：隔离计算进程，按Solver能力和资源队列扩展；
- Object Storage：模型资产、时间序列、大型数据集和导出文件；
- Observability：日志、指标、Trace、告警；
- Integration Adapters：LTI/OneRoster/OIDC/SAML及外部系统适配。

Redis如被引入，只用于缓存/限流等可丢失数据，不作为Session权威状态或唯一锁服务。

## 3. 环境策略

- Local：Docker Compose启动API、PostgreSQL、NATS、S3兼容存储、Worker和OTel Collector；
- CI：临时数据库和消息服务，执行迁移、单元、契约、集成和安全测试；
- Staging：与生产拓扑接近，使用合成/脱敏数据，验证升级、回滚和故障演练；
- Production：多副本API、受控Worker池、数据库高可用、持久消息、对象存储版本化和集中监控。

Apple Silicon本地开发需要验证容器镜像架构、Python科学计算依赖和Worker性能，不允许将本机表现直接外推到生产容量。

## 4. CI质量门禁

Pull Request必须执行：
1. 格式化、Lint、TypeScript类型检查；
2. Python静态检查和类型检查（选定工具后冻结）；
3. 单元测试和覆盖率阈值（阈值经代码基线后设定）；
4. OpenAPI/Schema/事件契约校验；
5. 数据库迁移和回滚检查；
6. PostgreSQL集成测试与真实RLS测试；
7. NATS Outbox/Consumer重复投递和重放测试；
8. Worker协议、fencing和故障注入测试；
9. 依赖、容器、Secret和License扫描；
10. 构建可追溯Artifact、SBOM和版本元数据。

测试未运行、被跳过或工具未安装时，状态必须明确为NOT RUN，不得标记PASS。

## 5. 测试分层

| 层级 | 重点 | 代表性用例 |
|---|---|---|
| Unit | 纯领域规则 | 状态迁移、单位换算、约束 |
| Contract | API/事件/Package契约 | Schema兼容、错误码、版本 |
| Integration | DB、RLS、NATS、对象存储 | Outbox事务、跨租户拒绝 |
| Worker | Solver与任务执行 | 输入/输出校验、超时、重试 |
| E2E | 学生/教师完整流程 | DC Circuit实验和评分 |
| Security | 威胁模型 | IDOR、SSRF、AI越权、恶意Package |
| Resilience | 故障恢复 | Worker崩溃、消息重复、DB中断 |
| Performance | 容量和延迟 | 并发Session、数据写入、图表读取 |
| Accessibility | 键盘和语义 | 学生实验关键任务可操作性 |

## 6. 可观测性

所有关键链路关联tenant_id（日志中按隐私策略脱敏/散列）、session_id、execution_id、command_id和correlation_id。指标至少包括：
- API latency/error rate；
- Command接受/拒绝/冲突和延迟；
- Session状态分布和启动成功率；
- Scheduler queue age、lease获取失败和过期；
- Worker耗时、超时、OOM、Solver失败；
- Outbox backlog、Consumer lag和重试；
- Observation写入/查询量、数据大小；
- Object Storage失败率和吞吐；
- Tenant配额、资源使用和单位实验成本。

告警必须有严重级别、值班责任、Runbook和关闭条件。日志不得包含认证令牌、学生敏感正文或完整秘密。

## 7. 备份、恢复与业务连续性

- PostgreSQL：全量备份+WAL/PITR，定期恢复演练；
- Object Storage：版本化、跨故障域复制（按数据区域要求）、digest校验；
- NATS：明确副本、保留、重放窗口和重建策略；
- Secrets：独立密钥管理和轮换；
- IaC/部署配置：版本控制、审批和回滚。

RPO/RTO不在设计阶段虚构，须根据机构合同、数据丢失影响、成本和架构能力评估后冻结。恢复演练必须验证数据库、对象数据、消息和外部身份配置的一致性。

## 8. 性能基准计划

基准测试前冻结工作负载模型：并发用户数、活跃Session数、每Session命令频率、Solver计算时长、Observation采样频率、时间序列规模、图表查询模式、Package资源大小和峰值登录。记录p50/p95/p99、吞吐、CPU/内存、数据库连接、队列等待和单位实验成本。

至少测试：
- API读写混合负载；
- 多Session并发命令；
- Worker队列积压和扩容；
- 长时间序列写入/读取；
- 大Package资源加载；
- 数据库故障转移；
- NATS重放和Consumer恢复。

## 9. 发布与回滚策略

数据库迁移采用向前兼容的expand/contract；应用先兼容新旧Schema，再分阶段移除旧字段。Package版本不可变；应用回滚不得改变已发布Package或Session快照。Worker与Solver版本必须记录，旧任务结果按兼容策略校验。发布采用分环境、灰度和健康检查；回滚条件包括错误率、数据一致性、安全告警和关键业务流程失败。

## 10. 试点/生产门禁

- 产品与科学：DC模型专家签核、参考算例通过；
- 安全与隐私：目标法域评估、数据目录、RLS、威胁模型和供应商审查通过；
- 可靠性：Outbox、NATS、Worker fencing、恢复演练通过；
- 体验：学生/教师任务可用性和设备矩阵通过；
- 运维：告警、Runbook、备份恢复、回滚和支持责任明确；
- 经济性：容量、配额和单位实验成本获得批准。
