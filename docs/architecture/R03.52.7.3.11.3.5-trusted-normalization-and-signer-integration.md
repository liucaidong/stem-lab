# R03.52.7.3.11.3.5 — Trusted Request Normalization and Signer Integration

**Status:** DESIGN / IMPLEMENTATION PARTIAL

## 1. Trusted path

1. Accept raw UTF-8 request bytes at the trusted ingress boundary.
2. Parse with duplicate-key rejection before converting into ordinary dictionaries/maps.
3. Reject invalid UTF-8, unpaired surrogates, non-JSON constants, unknown fields and unsupported contract versions.
4. Resolve trusted defaults before digest generation. The digest layer itself never supplies defaults.
5. Validate action-specific operation arguments and exact resource/action relationships.
6. Build the normalized Request Envelope using explicit fields and normalized integer units.
7. Produce canonical bytes using the versioned typed encoder.
8. Calculate SHA-256 and place the resulting sha256:hex value in the v2alpha2 signed Claim.
9. Serialize the complete Assertion payload deterministically, then sign the exact payload bytes with the approved Ed25519 key.
10. Pass the signed Assertion and the same normalized business arguments to the Store operation.

The signing key must not be exposed to untrusted Runtime code. The signer must own the normalization result and signing operation; an untrusted caller cannot supply a digest and ask the signer to attest to it.

## 2. Mutation-after-signing invariant

The Store must not trust the Runtime's copy of the normalized envelope or digest. It derives identity fields from the verified signed Claim and builds operation_arguments from the actual typed SQL parameters used by the mutation. Any change between signing and execution therefore changes the database digest and fails closed.

A request digest comparison is not a substitute for signature verification. A signature proves who asserted the digest; database recomputation proves that the actual operation parameters match that assertion.

## 3. Raw Assertion payload handling

The database verifier must:
- base64url-decode the exact payload bytes;
- reject invalid UTF-8;
- reject duplicate keys at every JSON object depth before jsonb conversion;
- validate the v2alpha2 discriminator and required claim set;
- verify Ed25519 over the exact original payload bytes;
- only then use the validated Claim values to build the request digest input.

PostgreSQL jsonb alone cannot prove the original payload had no duplicate keys because duplicate members are collapsed during conversion. A strict raw-json parsing step is required before any jsonb conversion.

## 4. v2alpha1 isolation

The v2alpha1 verifier remains unchanged. The v2alpha2 verifier is a separate explicit version branch:
- v2alpha1 requires its original field set and rejects v2alpha2-only fields.
- v2alpha2 requires contract_version=2alpha2, idempotency_key and request_digest.
- No "try v2alpha2 then fallback to v2alpha1" behavior is allowed.
- A v2alpha1 token cannot authorize a v2alpha2 action or digest-bound handler.

## 5. Implementation gap

The current repository branch contains the Python typed encoder and a PostgreSQL digest-conformance helper, but it does not yet contain the trusted signer integration or a v2alpha2 raw-payload verifier. The current SQL helper is a disposable conformance artifact, not a callable production authorization boundary. This work remains required before G4/G5 can be accepted.
