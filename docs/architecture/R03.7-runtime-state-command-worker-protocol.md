# R03.7 Runtime状态机、Command与Worker协议

- 版本：0.1；日期：2026-11-02
- 状态：技术契约草案；需Spike与故障注入验证
- 关联：R02.3 FR-RT、R02.5 E2E-04、R03、R03.6 TF-01/02/03

## 1. 设计目标与权威边界

Runtime是实验执行生命周期的权威管理者。它管理Session状态、命令顺序、状态版本、Execution授权、结果提交和事件。Solver只计算，不拥有Session；Worker只执行获批Execution，不直接更新权威Session；Renderer只发送命令并消费Read Model。

权威写路径：API→Command Handler→事务数据库。异步计算路径：Transactional Outbox→Scheduler→Worker→Result Commit Handler。Worker不得持有修改Session/State/Event表的数据库凭证。

## 2. Session状态机

持久化状态建议：
- created：Session已创建，依赖清单已锁定；
- ready：初始化和前置校验完成，可接受运行命令；
- running：存在有效执行或连续运行；
- paused：已在安全边界停止推进仿真时间；
- completed：达到实验终止条件；
- failed：不可恢复执行错误，等待显式重试/重置策略；
- cancelled：由授权主体取消。

resuming不作为持久化状态，Resume作为命令处理阶段；若未来需要长时间恢复过程，可在Execution状态中表达，不扩展Session主状态机。

主要迁移：
- created→ready：依赖解析、输入校验、初始状态建立成功；
- ready→running：Start；
- running→paused：Pause在当前可提交边界生效；
- paused→running：Resume；
- ready/paused/running→completed：满足模型终止条件或显式完成规则；
- 非终态→cancelled：授权Cancel；
- running→failed：不可恢复错误；
- failed→ready：显式Reset/Retry策略完成，且生成新Execution/恢复版本。

禁止迁移必须返回稳定错误码且不产生状态副作用。完成/取消为终态；重新实验创建新Attempt/Session，不复用终态Session。

## 3. Command语义

命令集合：Initialize、Start、Pause、Resume、Step、Reset、Cancel、SetParameter（受Package白名单约束）。

每个写命令必须携带command_id / Idempotency-Key、request_hash、expected_state_version、command_type和schema_version、payload、correlation_id。actor_id和tenant_id必须从认证上下文派生，不接受请求JSON自报。

同一幂等键：
- 同请求哈希：返回原CommandReceipt，不重复副作用；
- 不同请求哈希：返回IDEMPOTENCY_KEY_REUSE_CONFLICT；
- 保留期必须覆盖最大客户端重试窗口和审计要求，具体值由容量/业务评估冻结。

并发控制：按Session进行事务级串行化（行锁或等效机制）；校验expected_state_version；成功状态变更后递增state_version。冲突返回STATE_VERSION_CONFLICT并提供当前版本标识。不得依赖客户端时间排序。

## 4. 原子事务边界

一个命令事务必须原子写入CommandReceipt、RuntimeSession/RuntimeState、RuntimeEvent（aggregate_sequence单调递增）、Transactional Outbox和必要审计记录。任何一步失败均回滚，不允许状态已更新但事件/Outbox丢失。事务内不得执行长时间科学计算或网络RPC。

## 5. Step、Pause、Reset和Clock

- Start：创建Execution并将Session置为running。
- Pause：阻止新的Step调度；在途计算按边界策略完成或取消；仅在结果安全提交后报告paused。
- Resume：基于最近有效state创建新Execution或恢复执行计划；不可重用过期lease。
- Step：只在ready/paused状态接受，执行一个模型定义的step unit；只有验证通过的结果才推进Simulation Clock。
- Reset：恢复Package/Model定义的初始状态，递增state_version和epoch，废弃旧Execution；保留历史事件和Observation，不删除审计。
- Cancel：取消后续调度；迟到Worker结果由epoch/状态校验拒绝。

Clock分离：Wall Clock用于业务截止/审计时间；Monotonic Clock用于进程耗时；Simulation Clock用于模型时间；Render Clock用于画面刷新；Device Clock未来用于真实设备采样。Render FPS不得决定Simulation Step。

## 6. Execution与Worker Lease协议

Execution记录session_id、execution_id、input_state_version、epoch、solver_id/version、input_digest、status、attempt_no和deadline。

Scheduler租约字段：lease_id、lease_owner、lease_expires_at、fencing_token、epoch。fencing_token必须单调递增并由数据库/协调事务分配，不能仅依赖Worker本地时钟。

Worker请求只携带不可变输入快照和短期执行凭证。Worker结果包含execution_id、session_id、input_state_version、epoch、fencing_token、output_digest、solver_version、metrics和result_payload_ref。

结果提交必须验证Execution仍可提交；session_id和execution_id匹配；epoch与当前Session一致；input_state_version与Execution输入版本一致；lease/fencing token有效；Solver输出Schema、单位、范围和模型不变量通过；结果对象digest和大小符合策略。

任何检查失败都拒绝结果，不推进Session状态和Simulation Clock。重复结果返回原Receipt或稳定冲突，不产生第二次状态变化。

## 7. 失败与恢复矩阵

| 故障 | 处理 |
|---|---|
| Worker崩溃 | lease过期后Scheduler分配新Execution attempt |
| Scheduler崩溃 | 新Scheduler接管，递增fencing token/epoch |
| Worker迟到 | 旧epoch或token拒绝 |
| 消息重复 | Consumer按event_id/execution_id幂等 |
| 消息乱序 | 检查aggregate_sequence，不应用旧状态 |
| Solver超时 | Execution标记timeout/failed，Session保持最近有效状态 |
| 输出无效 | Validator拒绝，不推进Clock |
| 对象存储失败 | 不标记Execution成功；按幂等策略重试上传/清理 |
| DB提交失败 | 无Receipt/State/Event/Outbox部分写入 |
| 客户端断线 | 客户端重查Session权威状态和Receipt |

## 8. 必须实现的测试

状态迁移全覆盖；同幂等键同/异Hash；并发命令与过期stateVersion；事务中断；Outbox重复/乱序；Worker超时、崩溃、重启、迟到结果；lease过期接管；旧epoch拒绝；Reset保留历史；Clock推进边界；对象存储失败和结果重放。

## 9. 冻结前待决策

Step的领域粒度、Pause对在途求解的边界、Reset是否允许在running状态、Execution重试上限、幂等Receipt保留期、Outbox清理策略、事件重放窗口和fencing token具体实现，均须通过技术Spike与容量评估后记录ADR。
