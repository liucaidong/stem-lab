## 4. 故障注入场景

- DB在命令事务中断开；
- Outbox发布后但消息确认前Publisher崩溃；
- Consumer处理成功但Ack前崩溃；
- Scheduler持有Lease时被杀死；
- Worker计算完成后网络断开；
- Reset与Worker结果提交同时发生；
- Object Storage上传完成但数据库提交失败；
- RLS事务上下文在连接池复用时泄漏；
- Package解析遇到超大压缩包或恶意资源；
- API在Assignment截止时间边界收到并发提交。

每个场景必须验证系统状态、可恢复性、用户反馈、审计记录和重复副作用。

## 5. 数值验证

DC Circuit：
- 参考输入集由学科专家提供；
- 检查等效电阻、电流、元件压降、KVL和适用的功率关系；
- 单位和量纲错误必须被检测；
- 测量显示精度与模型数值误差分别报告。

RC Circuit：
- 选择可解析或高精度参考解；
- 测试步长变化下的误差趋势；
- 记录求解器版本、步长、容差、初始条件和环境；
- 检查Simulation Clock仅在有效结果提交时推进。

容差不得由实现者为使测试通过而事后调整，必须由科学依据和专家签核确定。

## 6. 参考算例与自动化验证工件

- DC：`contracts/examples/dc-circuit.reference-cases.json`，覆盖4组理想串联电路算例；自动检查等效电阻、欧姆定律、各元件压降、KVL和源功率/电阻耗散功率一致性。
- RC：`contracts/examples/rc-circuit.reference-cases.json`，采用理想RC充电解析解，覆盖t=0、1τ、2τ、5τ四个采样点；用于Runtime/ODE技术验证，不属于教学MVP。
- 可重复检查：`scripts/validate_contracts.py`；CI工作流：`.github/workflows/contract-validation.yml`。
- 当前浮点比较容差仅用于确定性参考数据的数值比较，不是Solver验收容差、仪器测量不确定度或教学显示精度。Solver误差阈值必须经步长收敛实验和学科评审后确定。
- 自动算例检查不等于专家签核、真实Solver验证或系统集成测试。

## 7. 性能测试设计

先建立工作负载模型，再设定目标。至少覆盖并发登录、活跃Session、命令速率、Solver耗时分布、Observation采样量、时间序列大小、Package加载、教师批量审阅和导出。记录p50/p95/p99、吞吐、CPU/内存、DB连接、队列等待、错误率和单位实验成本。

## 8. 验收证据模板

每次Spike/测试报告必须包含：
- Test ID、日期、执行者、审阅者；
- Git commit、依赖锁文件和镜像版本；
- OS/CPU/内存/数据库/消息服务配置；
- 测试数据和输入digest；
- 操作步骤、预期结果和实际结果；
- 日志、Trace、截图或机器可读报告；
- PASS/FAIL/BLOCKED/NOT RUN；
- 缺陷ID、严重级别、影响面和修复计划；
- 复测结果和关闭签核。
