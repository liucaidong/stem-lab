# R03.52.7.3.6.2–3.6.8 — PostgreSQL Job-Rooted Authorization Reference

- Status: executable reference harness; proposal only, not production authorization.
- Contract: worker resource assertion v2alpha1, unchanged.
- Scope: deterministic-per-key test issuer, Ed25519 database verification, persisted Job-to-Session binding, transaction-bound nonce consumption, RLS, privilege boundary, Job Complete, Job Renew, Job Fail, Job Retry, Job Dead-letter and Receipt Reconciliation.
- Explicit limitation: this increment implements Job Complete, Job Renew, Job Fail, Job Retry, Job Dead-letter and Receipt Reconciliation reference paths. Claim, DLQ Replay and Outbox Dispatch remain incomplete.

## 1. Test issuer

The test issuer builds a closed v2alpha1 claims object, serializes compact UTF-8 JSON with sorted keys, base64url-encodes the exact payload bytes, and signs the encoded payload segment with an ephemeral Ed25519 keypair generated inside the disposable PostgreSQL test process. Identical claims under the same in-process key produce identical token bytes. Private signing material is not persisted; PostgreSQL stores only the public key.

This is a deterministic serialization/signing harness, not production key custody, KMS/HSM integration, key rotation, or an approved issuer service.

## 2. Database trust boundary

The harness creates:
- a NOLOGIN, NOSUPERUSER, NOBYPASSRLS verifier role;
- a separate NOSUPERUSER, NOBYPASSRLS runtime role and a real login mapped to it;
- a public-key-only issuer keyring;
- Job, Session, Receipt, Transition, Outbox and nonce-ledger tables;
- SECURITY DEFINER functions with fixed search_path and schema-qualified references.

The verifier role is not granted to runtime. Runtime receives EXECUTE only on narrowly scoped authorization helpers and DML privileges on protected business tables. It receives no keyring or nonce-ledger table privileges.

A verifier-only RLS policy provides the SECURITY DEFINER owner with a limited internal read path. This policy is separate from runtime policies and must remain restricted to the non-login verifier role.

## 3. Authorization and relationship proof

The helper verifies the exact v2 claim set and JSON types, issuer/key lifecycle, Ed25519 signature, tenant, audience, action, Job, Session, owner, epoch, operation ID, validity interval and nonce. It verifies the action-specific resource root and reads the persisted Job row to prove Job-to-Session equality and current owner/epoch/running state/DB-clock lease validity.

The actual Job UPDATE remains fenced by exact tenant/job/session/owner/epoch and lease_expires_at greater than clock_timestamp() predicates. A prior authorization result never replaces the conditional mutation predicate. If a conditional mutation affects no row, the Unit of Work must roll back rather than commit a consumed nonce without its intended business operation.

The executable PostgreSQL harness currently authorizes worker.job.complete, worker.job.renew, worker.job.fail, worker.job.retry, worker.job.dead_letter and worker.receipt.reconcile. The receipt reconciliation path is separately rooted at the exact Receipt operation ID and uses a fresh nonce. Other action handlers remain explicitly unimplemented.

## 4. Job lease renewal

The reference exposes a narrow SECURITY DEFINER renew_v2(token, lease_seconds) function. It first validates and consumes the Job-rooted worker.job.renew capability, then conditionally updates only lease_expires_at using the persisted tenant/Job/Session/owner/epoch, running state and DB-clock unexpired predicate. The verifier role has a dedicated internal UPDATE policy and only the lease_expires_at column grant; the runtime role has no direct lease-column update privilege. The 5–3600 second duration bound is a test-harness guardrail, not a production lease policy decision.

## 5. Job failure transition

The reference exposes fail_v2(token), which validates and consumes the exact Job-rooted worker.job.fail capability, conditionally transitions the current fenced Job from running to failed, and inserts the Transition and Outbox event in the same database function transaction. A conflicting Outbox event is used as a fault injection: the function returns failure and the Job transition, Transition row and nonce consumption all roll back. Runtime cannot directly write the failed terminal state; the verifier-only function owns that narrow mutation path.

## 6. Retry and Dead-letter transitions

The reference exposes retry_v2 and dead_letter_v2 as separate SECURITY DEFINER operations. Retry uses the persisted attempt_count/maximum_attempts ceiling, a DB-clock available_at, a stable error-code allowlist, and clears the previous owner/lease. Dead-letter requires an explicit non_retryable reason or a persisted maximum-attempt condition, creates the exact DLQ item, and emits Transition plus Outbox records. Both operations conditionally update the current tenant/Job/Session/owner/epoch and unexpired lease. Their Job state mutation, nonce consumption, Transition, Outbox and DLQ insertion share one function transaction. Injected unique conflicts verify that the whole operation rolls back, including nonce consumption.

The retry delay range and error-code pattern are reference-test guardrails, not approved production retry policy. The test dead-letter function models the max-attempt predicate against the persisted per-Job maximum; it does not implement the global Retry Policy Registry.

## 7. Receipt, idempotency and ambiguous-commit reconciliation

The reference now supports a distinct worker.receipt.reconcile capability. Its resource root is the exact Receipt operation ID; it cannot be substituted for the Job-rooted completion capability. Reconciliation is permitted only when the persisted Receipt matches tenant, Job, Session and operation ID.

A simulated lost commit acknowledgement is resolved in a new transaction with a fresh assertion and nonce. The stored request digest is compared with the retry digest: equality yields DUPLICATE; inequality yields IDEMPOTENCY_CONFLICT. The harness models the ambiguous outcome by committing the first Unit of Work and intentionally treating its result as unobserved; it does not claim to reproduce a real network partition during COMMIT.

## 8. Transaction-bound nonce ledger

The nonce ledger has a unique issuer/kid/nonce key and stores the exact signed token, authorization scope and current transaction ID from pg_current_xact_id().

- First valid use inserts the ledger row in the same transaction as business writes.
- Repeated use of the identical capability in that transaction is allowed.
- Reuse in a later transaction is rejected after the original commits.
- Concurrent duplicate use serializes on the unique constraint; at most one transaction can commit the nonce.
- Rollback removes the nonce row together with business writes.

No production retention or cleanup period is selected. Production retention must cover assertion lifetime, clock skew, recovery, audit and incident-response windows.

## 9. RLS and GUC semantics

The transaction-local GUC carries the signed token but is not authority. RLS requires a matching nonce-ledger row for the current transaction, exact token, tenant, Job, Session, action and resource root. A caller-set GUC without successful database authorization is insufficient.

RLS is enabled and forced on protected tables. Runtime is a real non-superuser login mapped to a non-owner role with NOBYPASSRLS. The harness verifies keyring/nonce-ledger isolation and denial of verifier-role escalation.

## 10. Implemented test coverage

- valid Ed25519 Job-rooted capability and complete UoW writes;
- Job lease renewal with DB-clock expiry and single-use nonce;
- Job failure transition with atomic Transition/Outbox and nonce rollback on injected conflict;
- retry scheduling, attempt ceiling, lease release and DB-clock available_at;
- dead-letter DLQ item, terminal Transition/Outbox and atomic rollback on DLQ conflict;
- fresh Receipt-rooted reconciliation after a simulated ambiguous commit;
- same-digest DUPLICATE and changed-digest IDEMPOTENCY_CONFLICT outcomes;
- deterministic token bytes for identical claims and in-process key;
- signature tampering, unknown claim and malformed expiry rejection;
- wrong tenant, Job, Session, owner, epoch and audience;
- missing authorization despite populated GUC;
- persisted DB lease expiry;
- stale Worker owner/epoch denial after reassignment;
- same-transaction repeated assertion;
- committed cross-transaction replay rejection;
- rollback atomicity for nonce and business writes;
- concurrent duplicate nonce race;
- runtime inability to read keyring/nonce ledger or assume verifier role;
- forced RLS on protected data;
- cross-session/cross-tenant child-row splice rejection;
- Complete capability cannot perform a different terminal transition.
