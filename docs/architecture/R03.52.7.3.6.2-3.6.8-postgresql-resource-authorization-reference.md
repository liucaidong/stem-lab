## 1. Implemented operation coverage

| Operation | Capability root | Reference handler |
|---|---|---|
| Claim | Persisted worker assignment + allowed job types; no tenant/job claim input | `claim_next_v1` with `FOR UPDATE SKIP LOCKED`, DB-clock lease, attempt increment and epoch increment |
| Renew | Exact Job | `renew_v2`; DB-clock lease extension and current owner/epoch fence |
| Complete | Exact Job | Runtime RLS-protected Job/Receipt/Transition/Outbox Unit of Work |
| Fail | Exact Job | `fail_v2`; terminal Job state + Transition + Outbox atomically |
| Retry | Exact Job | `retry_v2`; attempt ceiling, DB-clock `available_at`, lease release and events |
| Dead-letter | Exact Job | `dead_letter_v2`; DLQ item + terminal state + Transition + Outbox atomically |
| DLQ Replay | Exact DLQ item | `replay_dlq_v2`; persisted replay principal, replay limit, new Job/new epoch |
| Outbox Dispatch | Exact Outbox event | `dispatch_outbox_v2` + `ack_outbox_v2`; separate dispatcher identity, lease epoch and acknowledgement |
| Idempotent retry / ambiguous commit | Exact Receipt operation ID | `worker.receipt.reconcile`; fresh assertion/nonce and digest comparison |

These are reference handlers in a disposable security fixture. They are not a production Store Adapter, and the tests do not establish production readiness.

## 2. Versioned capability contracts

- `contracts/worker-resource-assertion.schema.v2alpha1.json`: Job-rooted worker operations plus exact Receipt, DLQ item and Outbox event roots. v1alpha1 remains unchanged.
- `contracts/worker-job-lease.schema.v2alpha1.json`: versioned lease context includes `session_id`; the lease object itself is not authority.
- `contracts/worker-claim-assignment.schema.v1alpha1.json`: separate Claim capability with issuer/key, worker subject, assignment ID, job-type allowlist, time bounds and nonce. It deliberately has no `tenant_id` or `job_id`.
- Claim authorization verifies the requested job-type set is a subset of the persisted assignment allowlist. Tenant selection is performed only by the database queue query.

## 3. PostgreSQL trust boundary

The fixture creates a NOLOGIN/NOSUPERUSER/NOBYPASSRLS verifier role; a separate non-owner runtime role and login; a dedicated dispatcher login; and a dedicated DLQ replay login. None is a superuser, table owner or RLS bypass role. Runtime, dispatcher and replay principals do not inherit verifier privileges.

SECURITY DEFINER functions use fixed `search_path`, schema-qualified object references, no dynamic SQL, and least-privilege grants. The verifier role owns the helper functions but not the protected tables. Verifier-only RLS policies provide limited internal reads and narrowly scoped mutation paths.

Protected data includes Job, Session, Receipt, Transition, Outbox, DLQ item, worker assignment, dispatcher assignment, replay-principal grants and both nonce ledgers. RLS is enabled and forced on protected tables.

## 4. Job-rooted operations

### Complete

The runtime must first consume the exact signed Job capability. RLS then requires a matching nonce-ledger row for the current transaction, exact token, tenant, Job, Session, action, resource root and operation ID. The Job transition is constrained to `running` → `succeeded`; runtime has column-level UPDATE permission only for `status`. Receipt, Transition and Outbox writes share the same Unit of Work.

### Renew

`renew_v2` validates the action before nonce consumption, verifies current persisted owner/epoch/running state and an unexpired DB-clock lease, then updates only `lease_expires_at`. The verifier role has the narrow column grant; runtime cannot directly update lease, owner or epoch. A lost fencing predicate raises inside the function so nonce consumption rolls back.

### Fail

`fail_v2` performs the exact fenced `running` → `failed` transition and inserts Transition plus Outbox rows in the same function transaction. A conflicting Outbox event is used for fault injection; the Job update, Transition and nonce all roll back together.

### Retry

`retry_v2` checks persisted `attempt_count < maximum_attempts`, validates the stable error-code shape, sets `available_at` from `clock_timestamp()`, preserves the completed-attempt count until the next Claim, and releases the prior owner/lease. Transition and Outbox rows are atomic with the state change. Delay and error-code bounds are reference-test guardrails, not approved production retry policy.

### Dead-letter

`dead_letter_v2` accepts an explicit `non_retryable` reason or requires the persisted maximum-attempt condition. It creates the exact DLQ item, transitions the Job to `dead_lettered`, releases owner/lease, and emits Transition plus Outbox rows atomically. Injected DLQ uniqueness conflicts verify rollback of all effects and nonce consumption.

## 5. Tenant-neutral Claim

Claim uses a distinct `worker-claim-assignment.v1alpha1` assertion because the target Job and Tenant are not yet known. The database verifies the worker assignment, the requested job-type subset, and the assignment's persisted tenant allowlist; neither tenant nor Job is supplied by the caller. It consumes a dedicated assignment nonce, then selects an eligible Job within that persisted scope with `FOR UPDATE SKIP LOCKED`. It increments the persisted epoch, assigns the worker owner, and sets lease expiry using the database clock. The function accepts no tenant argument.

The same Claim token can return the same claimed Job within its original transaction, but cannot claim a second Job in that transaction or be replayed in a later transaction. Concurrent distinct claims are tested against distinct queued rows.

## 6. DLQ Replay

Replay is rooted at the exact DLQ item and requires a persisted `(tenant, dlq_item, principal)` replay grant with an enabled flag and `max_replays`. The replay function consumes a fresh nonce, increments the replay counter, and creates a new queued Job with a new Job ID and epoch 1. It does not reuse the dead-lettered Job's old Worker lease. New Job, replay counter, Transition, Outbox and nonce are atomic. A replay limit and injected primary-key conflict are tested.

## 7. Outbox Dispatch and acknowledgement

Outbox dispatch uses a dedicated dispatcher identity and exact `outbox_event` resource root. `dispatch_outbox_v2` claims a pending or expired event lease using DB time and increments `dispatch_epoch`; it returns the event payload. After external delivery, `ack_outbox_v2` requires the current dispatcher owner, epoch and unexpired lease before marking the event dispatched.

An expired dispatch lease may be reclaimed with a fresh capability and a higher epoch; an old acknowledgement is rejected. Delivery is at-least-once, not exactly-once. Consumers must deduplicate on the stable event ID. The reference functions do not perform external network delivery.

## 8. Receipt, idempotency and ambiguous commit

A separate `worker.receipt.reconcile` capability is rooted at the exact Receipt operation ID and uses a fresh nonce. The harness commits the original Unit of Work while treating its result as unobserved, then resolves the durable Receipt in a new transaction. Equal request digests yield `DUPLICATE`; changed digests yield `IDEMPOTENCY_CONFLICT`. This simulates the reconciliation contract but does not reproduce a real network partition during COMMIT. The current reference INSERT policy only checks that `request_digest` is non-empty and bounded; it does not cryptographically bind that digest into the assertion. Before production, either add a signed digest claim and enforce equality at INSERT, or compute the digest inside a trusted server-side boundary.

## 9. Nonce, replay and transaction semantics

The Job/Receipt/Outbox/DLQ nonce ledger uses unique `(issuer,kid,nonce)` and stores the exact token, scope and `pg_current_xact_id()`. Claim uses a separate assignment nonce ledger because no Tenant/Job exists at authorization time.

- Identical capability reuse is permitted only inside its original transaction where explicitly supported.
- A committed nonce replay in a later transaction is rejected.
- Unique constraints serialize concurrent duplicate use.
- Rollback removes nonce consumption with the business effects.
- Claim token reuse cannot switch signed claims even when issuer/key/nonce are identical.
- No production nonce retention or cleanup interval is selected.

## 10. RLS and privilege boundary

Transaction-local GUCs carry the signed assertion but are not authority. Policies require a matching verifier-created nonce ledger row for the current transaction and exact scope. Runtime cannot read issuer keys or nonce ledgers, cannot assume verifier, and cannot directly mutate Job owner/epoch/lease. Dispatcher and replay logins cannot read their protected tables or assume verifier; they can invoke only their narrowly granted functions.

Residual trust boundaries remain: database superuser/host compromise, issuer compromise, malicious trusted administrators, and production key custody/deployment controls are not defeated by this fixture.

## 11. Test coverage

The PostgreSQL harness also simulates connection-pool return hygiene: transaction-local assertion GUCs must disappear at transaction end, and session-level role/GUC state must be reset before reuse. The PostgreSQL harness covers signature tampering and malformed claims; Job/Session and owner/epoch/lease checks; Complete, Renew, Fail, Retry and Dead-letter; Receipt reconciliation and digest conflict; Claim assignment and job-type allowlist; `SKIP LOCKED` concurrency; DLQ replay grants/limits/new Job epoch; Outbox dispatch lease/ack/reclaim; cross-tenant/session child-row splicing; role isolation; nonce same-transaction behavior, cross-transaction replay, concurrent duplicate races, rollback atomicity and injected uniqueness failures.

CI validation of the Python/JSON contract suite and PostgreSQL test job is required before acceptance. A test run that is pending, failed or still building must not be reported as successful.
