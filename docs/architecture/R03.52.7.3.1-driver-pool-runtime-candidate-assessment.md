# R03.52.7.3.1 — PostgreSQL Driver, Pool & Runtime Candidate Assessment

- Date: 2026-11-02
- Status: candidate assessment; no implementation technology selected
- Related: DEC-03, DEC-04, DEC-14, DEC-19, DEC-30
- Store Protocol v1alpha1: PASS (contract)
- Product Code Freeze: ACTIVE; P3.17: OUT OF SCOPE

## 1. Decision summary

Do not select a driver or pool from microbenchmarks alone. The Store Protocol and Unit of Work contract is now driver-neutral; candidates must be tested against the same RLS/tenant verifier, fencing predicates, idempotency, cancellation, ambiguous commit and connection-reset workload.

**Preferred candidate pairing for the current architecture:**
- Python Worker, if retained: Psycopg 3 + psycopg_pool. Use the sync pool for a synchronous worker runtime or AsyncConnectionPool for an asyncio runtime.
- TypeScript API, if selected: node-postgres (`pg`) + its built-in `pg-pool`, with an explicit checked-out Client per Unit of Work.
- asyncpg remains the principal Python asyncio performance challenger.
- SQLAlchemy 2.x is an optional SQL toolkit/ORM and engine/pool abstraction, not an independent PostgreSQL wire driver. Evaluate it only if ORM/Core productivity or cross-dialect support has demonstrated value.
- postgres.js is a secondary TypeScript candidate; its default query pipelining requires explicit compatibility testing against transaction poolers.
- Do not select a library until DEC-03 runtime and DEC-14 database deployment/provider are decided.

This is a recommendation for benchmarking priority, not an approved production stack.

## 2. Python candidates

### 2.1 Psycopg 3 + psycopg_pool — first benchmark priority

Verified capabilities from the official documentation:
- Sync and asyncio interfaces are available in the same driver family.
- DB-API 2.0 interface, COPY support, static typing, server-side binding, prepared statements, pipeline mode and direct libpq access.
- Pool package exposes synchronous ConnectionPool, AsyncConnectionPool and NullConnectionPool.
- Pool supports bounded max_size, acquisition timeout, max_waiting, connection check/reset hooks, connection lifetime/idle controls and reconnect behavior.
- Pool connection context commits on normal exit, rolls back on exception and replaces broken connections.
- Async task cancellation asks PostgreSQL to cancel the running operation; cancellation does not prove the operation did not complete, so transaction rollback and outcome reconciliation remain necessary.

Why it fits:
- One driver family can serve synchronous and asynchronous Worker runtimes without changing the Store Protocol.
- Native libpq behavior is familiar to PostgreSQL operations teams.
- Explicit Unit of Work maps cleanly to a checked-out pooled connection and transaction context.
- Pool lifecycle hooks provide places to enforce connection validation and tenant-context cleanup.

Risks to validate:
- libpq/OpenSSL/system package compatibility in deployment images;
- cancellation and ambiguous commit handling;
- pool reset/check callbacks must not silently return a connection with an open transaction or leaked session state;
- psycopg_pool is a separate package and must be version-pinned independently.

Official sources:
- https://www.psycopg.org/psycopg3/docs/
- https://www.psycopg.org/psycopg3/docs/api/pool.html
- https://www.psycopg.org/psycopg3/docs/advanced/pool.html
- https://www.psycopg.org/psycopg3/docs/advanced/async.html

### 2.2 asyncpg — asyncio performance challenger

Verified capabilities:
- Native asyncio PostgreSQL driver implementing the PostgreSQL binary protocol.
- Built-in async connection pool with min/max sizing, acquire timeout, max query count, idle lifetime, connection setup/reset hooks and connection expiry.
- Explicit transaction context managers and nested transactions/savepoints.
- Pool reset clears transaction/session state including configuration variables and advisory locks.
- Official documentation warns that prepared statements can fail through PgBouncer transaction/statement pooling unless automatic statement caching is disabled (for example `statement_cache_size=0`).

Why benchmark it:
- It is a focused asyncio-native driver and is a plausible high-throughput Worker candidate.
- It exposes lower-level PostgreSQL behavior without requiring an ORM.

Risks:
- It is not a DB-API driver; adapter code and ecosystem integration are more specialized.
- Prepared statement behavior must be profiled against the exact pooler mode/version.
- Cancellation, release/reset and ambiguous commit semantics need explicit fault-injection tests.

Official sources:
- https://magicstack.github.io/asyncpg/current/
- https://magicstack.github.io/asyncpg/current/api/index.html
- https://magicstack.github.io/asyncpg/current/usage.html
- https://magicstack.github.io/asyncpg/current/faq.html

### 2.3 SQLAlchemy 2.x — optional abstraction, not a wire-driver competitor

SQLAlchemy's AsyncEngine uses a dialect/driver underneath (for example asyncpg or psycopg) and provides its own Engine/Pool and transaction abstractions. Therefore compare:
- psycopg + psycopg_pool directly;
- asyncpg directly;
- SQLAlchemy AsyncEngine + asyncpg;
- SQLAlchemy AsyncEngine + psycopg.

Do not compare “SQLAlchemy vs asyncpg” as if they were mutually exclusive drivers. Measure the additional abstraction cost and whether the application actually needs ORM identity mapping, declarative models or SQL compilation. For the current Store contract, explicit SQL and transaction boundaries are likely simpler; SQLAlchemy should not be introduced merely to obtain a pool.

Official sources:
- https://docs.sqlalchemy.org/en/20/dialects/postgresql.html
- https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html
- https://docs.sqlalchemy.org/en/20/core/pooling.html

## 3. TypeScript / Node candidates

### 3.1 node-postgres (`pg`) + pg-pool — first benchmark priority for a TypeScript API

Verified capabilities:
- Built-in pool with max connection count, idle timeout, connection timeout and max lifetime controls.
- Transactions are explicit and low-level: all statements in a transaction must use the same checked-out Client; `pool.query()` must not be used to compose a multi-statement transaction.
- The checked-out client must always be released; the pool queues waiters when all clients are busy.
- Query pipelining is opt-in and defaults off in the documented client configuration.

Why it fits:
- Clear transaction ownership maps directly to the Store Unit of Work contract.
- Mature, widely used Node.js PostgreSQL interface with low abstraction overhead.
- Drizzle or another query builder can be layered on top without moving transaction ownership away from the Store adapter.

Risks:
- Application must implement transaction cleanup, rollback, client release and connection destruction after uncertain state correctly.
- Cancellation and statement-timeout behavior must be fault-tested.
- Per-process pool sizing must be included in the global database connection budget.

Official sources:
- https://node-postgres.com/features/pooling
- https://node-postgres.com/features/transactions
- https://node-postgres.com/apis/pool
- https://node-postgres.com/apis/client

### 3.2 postgres.js — secondary candidate

postgres.js supports Node.js and Deno and includes pooling, transactions and query pipelining. However, its default pipelining behavior is a compatibility risk when using a transaction-mode pooler: Supabase's official connection guide explicitly warns that transaction mode does not support pipelining and documents postgres.js-specific failure caveats.

It remains a benchmark candidate only if:
- pipelining can be disabled or safely constrained in the selected deployment;
- prepared statement behavior matches the actual pooler;
- transaction and cancellation tests pass under pooler failover and connection reuse.

Official sources:
- https://github.com/porsager/postgres
- https://supabase.com/docs/guides/database/connecting-to-postgres

## 5. Connection pooler compatibility

The deployment may use direct PostgreSQL connections, PgBouncer session pooling, PgBouncer transaction pooling or a provider-specific proxy. This choice changes driver configuration.

Required rules:
- Tenant context must be installed transaction-locally inside every UoW. Never depend on session-level tenant state surviving pool checkout.
- Prepared statement support depends on the exact PgBouncer/provider version and pool mode. Do not globally disable or enable prepared statements without a compatibility test.
- Transaction pooling returns a server connection after each transaction; session-level GUCs, advisory locks, cursors and temporary tables cannot be assumed to persist.
- Query pipelining is not allowed unless the selected proxy explicitly supports it and the benchmark proves correct ordering and result/error association.
- Application pool and server-side pooler limits must be budgeted together; avoid uncontrolled double pooling.

The final provider/version and pool mode are DEC-14 inputs, not library defaults.

## 6. Benchmark protocol

### 6.1 Fixed environment

Use the same PostgreSQL major/minor, schema, indexes, RLS policies, Ed25519 verifier, dataset, SQL statements, transaction isolation, network path and hardware for every candidate. Run at least:
- direct PostgreSQL connection;
- the intended production pooler mode once DEC-14 is known.

CI is suitable for functional conformance and smoke measurements only. Performance decisions require a controlled, repeatable benchmark host and recorded CPU/memory/network details.

### 6.2 Workload profiles

1. Claim: eligible Job lookup, row lock/skip locked, owner/epoch update, commit.
2. Renew: fenced owner/epoch/expiry update, commit.
3. Complete: Job + Session lock, revision check, Receipt + Transition + Outbox + Job update, commit.
4. Fail/retry: fenced state transition, retry schedule or DLQ, outbox, commit.
5. Tenant RLS: same queries with signed assertion verification and pool reuse.
6. Contention: concurrent claimers competing for a hot tenant queue and a balanced multi-tenant queue.
7. Cancellation: cancel before statement dispatch, during query, during COMMIT and during pool release.
8. Fault: database restart, connection reset, network drop during COMMIT, pool exhaustion and reconnect.
9. Context leakage: reuse a physical connection across tenants; prove transaction-local context is absent after commit, rollback and cancellation.
10. Proxy compatibility: prepared statement cache, pipeline behavior and session-state reset through the exact selected pooler.

### 6.3 Metrics

Record:
- throughput (ops/sec) and successful business transactions/sec;
- p50/p95/p99 transaction latency;
- p50/p95/p99 pool acquisition wait;
- active/idle/waiting connections and queue depth;
- PostgreSQL CPU, memory, lock waits, deadlocks and transaction age;
- error rate by stable StoreErrorCode;
- cancellation completion time and connection discard rate;
- ambiguous commit detection/reconciliation success;
- tenant-context leak count (must be zero);
- per-process pool size and total connection budget.

### 6.4 Load points

Run concurrency 1, 8, 32, 64 and 128 with fixed operation mix, then repeat under contention and fault injection. Use warm-up, at least 5 measured repetitions and report median plus spread. Do not compare results across different GitHub-hosted runners as a production performance ranking.

## 7. Preliminary recommendation

- **Python Worker:** benchmark Psycopg 3 sync and async pools first; use asyncpg as the primary challenger if the Worker runtime is asyncio.
- **TypeScript API:** benchmark node-postgres pg-pool first. Keep Drizzle optional as a query builder, not the transaction owner.
- **SQLAlchemy:** add only if ORM/Core benefits are concrete and the extra layer passes the same UoW conformance and performance thresholds.
- **postgres.js:** do not make it the default until transaction-pooler/pipeline compatibility is proven.
- Use separate per-process pools for API and Worker, with a centrally calculated connection budget. Never size pools independently without considering replica count and database max_connections.

No candidate is selected here. DEC-03 runtime, DEC-14 deployment/provider and the controlled benchmark results remain required inputs.
