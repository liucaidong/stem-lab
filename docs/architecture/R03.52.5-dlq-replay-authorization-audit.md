# R03.52.5 DLQ Replay Authorization & Audit Preflight

- Date: 2026-11-02
- Status: Executable authorization-preflight reference + schema/tests; CI pending
- Parent: R03.51 / R03.52.4
- Product Code Freeze: ACTIVE
- P3.17: OUT OF SCOPE / MUST NOT ENTER
- Related decisions: DEC-16, DEC-19, DEC-30

## 1. Objective

Define a fail-closed, auditable DLQ replay preflight. Replay never mutates the original dead-lettered Job into a new attempt. It creates a plan for a distinct new Job ID and binds the request to tenant, source Job, actor, reason, authorization action and policy version.

## 2. Authorization contract

The caller must supply an authorization decision scoped to:
- action = worker.dlq.replay;
- exact actor_id;
- exact tenant_id;
- exact source job_id;
- allowed = true;
- non-empty authorization policy version.

The reference function does not authenticate the actor or mint this decision. Production authorization must be derived from a trusted identity/authorization service; caller-provided booleans are not a security boundary.

## 3. Replay invariants

1. Source Job must be dead_lettered.
2. Original source Job and DLQ evidence remain immutable.
3. Replay creates a distinct new Job ID; ID generation is injected, not selected here (DEC-16 OPEN).
4. Replay request has a stable request_id for future idempotency.
5. Actor and human-readable reason are mandatory and retained in the audit plan.
6. Replay count must remain below configured replay_limit.
7. Authorization must match action + actor + tenant + source Job exactly.
8. Authorization policy version is retained for audit.
9. The function produces a plan only; it does not write Job, DLQ or audit tables.

## 4. Required production transaction (not implemented)

A future Store adapter must perform, in one transaction:
1. lock source Job and DLQ row;
2. re-check dead_lettered state, replay_count and replay_limit;
3. revalidate authorization and policy version;
4. reserve tenant-scoped request_id idempotency key;
5. insert new Job with distinct ID and controlled payload copy;
6. increment source DLQ replay_count;
7. append immutable audit record with actor/reason/policy version;
8. commit.

Concurrent replay requests must serialize on the source DLQ row. Same request_id/same digest must replay the prior receipt; same key/different digest must conflict. The original DLQ record must remain available for audit.

## 5. Executable assets

- runtime/dlq_replay.py: authorization preflight and immutable ReplayPlan.
- contracts/dlq-replay-plan.schema.v1alpha1.json: machine-readable plan schema.
- contracts/examples/dlq-replay-plan.valid.json: representative plan.
- scripts/validate_dlq_replay.py: schema and identity invariant check.
- scripts/test_dlq_replay.py: authorization scope, state, reason, replay limit and new-ID tests.

## 6. Explicit limitations

- No authentication or trusted authorization decision issuer.
- No production DB transaction, request idempotency table or audit ledger.
- No actual Job payload copy, queue insertion or execution.
- No operator UI/CLI, approval workflow or break-glass process.
- No tenant-context trust boundary; DEC-19 remains OPEN.
- No primary ID strategy; DEC-16 remains OPEN.
- No event relay or replay side-effect policy; DEC-30 remains OPEN.

Passing tests verify the preflight function only, not production DLQ replay capability.
