# R03.52.7.3.11.3.2 — Request Envelope, Operation Binding, Receipt and Atomicity

**Status:** DESIGN SPECIFICATION / CANDIDATE / NOT APPROVED

## 1. Envelope contract

The Request Envelope is a normalized business command, not a copy of the Assertion. The following fields are required and participate in the digest:

| Field | Type | Required | Null / absent | Digest | Rule |
|---|---|---:|---|---:|---|
| contract_version | string | yes | forbidden | yes | exactly 2alpha2 |
| action | string | yes | forbidden | yes | exact enumerated operation |
| tenant_id | string | yes | forbidden | yes | 1..256 UTF-8 bytes after scalar validation |
| job_id | string | yes | forbidden | yes | stable Job identifier |
| session_id | string | yes | forbidden | yes | stable Session identifier |
| resource_type | string | yes | forbidden | yes | action-specific enum |
| resource_id | string | yes | forbidden | yes | Job ID, Receipt operation ID, Outbox event ID or DLQ item ID according to action |
| operation_id | string | yes | forbidden | yes | unique execution/transition identity |
| idempotency_key | string | yes | forbidden | yes | client/business retry identity; not interchangeable with operation_id |
| operation_arguments | object | yes | empty object allowed only for no-argument actions | yes | exact action-specific allowlist |

All strings are exact Unicode scalar sequences encoded as UTF-8. No NFC/NFD normalization or trimming is performed. Identifiers reject C0 controls and DEL. No default values are injected into the digest layer: defaults must be materialized by trusted normalization before digest creation. Absent object members differ from explicit null. Null is permitted only where the action-specific schema explicitly allows it; current action argument schemas do not allow null.

Arrays, where later admitted by an action schema, preserve order. Object keys are sorted by raw UTF-8 bytes. Duplicate keys are rejected during strict raw JSON parsing. Unknown fields are rejected. Floating-point values are rejected. Integers use signed int64. Duration values use integer units (seconds or microseconds) rather than binary floating point. Timestamps are not currently permitted as generic operation arguments; future time fields must use integer epoch microseconds with an explicit field name and unit.

The current reference codec supports recursive null/boolean/integer/string/array/object tags as a codec primitive, but each action allowlist is narrower. Adding a field or value type requires a new reviewed schema/compatibility decision.

## 3. Assertion binding

The v2alpha2 signed Claim set includes contract_version=2alpha2, idempotency_key and request_digest. The signature covers the complete payload bytes and therefore these claims. The digest covers the Request Envelope listed above. Assertion identity/time/nonce/owner/epoch remain signed and independently validated, but are not duplicated into the Request Envelope.

The database constructs the digest input from:
- envelope identity fields read from the verified signed Claim, not caller-supplied tenant/job/resource IDs;
- operation_arguments constructed from the exact typed SQL function parameters that are subsequently used by the SQL statements;
- idempotency_key read from the verified Claim and used as the Receipt identity.

A caller-supplied digest is never used as the recalculation input. A caller-supplied envelope is not sufficient proof of the executed parameters.

## 4. Receipt identity and semantics

Proposed uniqueness key: (tenant_id, action, idempotency_key). The Receipt stores operation_id, request_digest, resource identity, outcome, stable result reference, and created/updated timestamps. A unique constraint on (tenant_id, action, idempotency_key) serializes competing first submissions. The operation_id remains a distinct immutable operation identity and should have its own unique constraint within tenant scope.

| Existing key | Incoming digest | Result |
|---|---|---|
| same tenant/action/idempotency key | same | return original Receipt/result; do not repeat business effects |
| same tenant/action/idempotency key | different | deterministic IDEMPOTENCY_CONFLICT; no mutation |
| different idempotency key | same | distinct operation identity; execute subject to authorization and state predicates |
| retry with new Assertion and new nonce | same | reconcile existing Receipt; no duplicate transition/outbox |
| replay old Assertion/nonce | any | reject through durable nonce uniqueness |
| digest mismatch | any | reject before Receipt insertion or business mutation |

Receipt lookup is itself resource-scoped and authorized. A caller cannot use a guessed idempotency key to read another tenant's Receipt. The unique constraint is the concurrency arbiter; application pre-checks are advisory only.

## 5. Transaction ordering

The proposed Unit of Work ordering is:

1. Parse raw Assertion payload without duplicate keys; validate v2alpha2 version and schema.
2. Verify Ed25519 signature and issuer key lifecycle.
3. Validate audience, action, tenant, Job, Session, resource, owner, epoch and database-clock lease fences.
4. Build canonical Request Envelope from verified claims + actual SQL function parameters.
5. Recalculate SHA-256 inside PostgreSQL and compare to signed request_digest.
6. Resolve Receipt idempotency identity under unique constraint/row lock.
7. Consume nonce in durable nonce ledger.
8. Apply Job/resource state transition.
9. Insert Receipt, Transition and Outbox rows.
10. Return a result only after all writes are part of the same outer transaction.

The exact relative ordering of nonce insertion and Receipt conflict resolution must be proven with savepoint/exception semantics. The invariant is stronger than a preferred statement order: every rejected digest, conflict or state predicate leaves no durable nonce, Receipt, Job mutation, Transition or Outbox effect. A successful reconciliation may consume a fresh nonce and return the original Receipt, but must not repeat business effects.

## 6. Concurrency and locking

- Unique index on (tenant_id, action, idempotency_key) is the serialization point for first-use idempotency.
- Use INSERT ... ON CONFLICT only with a follow-up read that compares the stored digest and returns a stable conflict for mismatch.
- A same-key/different-digest race must have one deterministic winner; the loser observes the committed Receipt and conflicts.
- Job state changes lock/fence the exact Job row and compare owner, epoch, session and DB-clock lease expiry in the mutation predicate.
- Receipt and Job lock ordering must be fixed across all handlers to avoid deadlocks. Candidate order: Job row, then Receipt identity row; reconcile-only reads lock Receipt only. This order requires validation against actual call graph before implementation.
- Nonce uniqueness is (issuer, kid, nonce). Duplicate nonce never becomes a successful replay merely because operation ID matches.
- No external broker/network side effect occurs inside the database transaction. Outbox publication remains at-least-once; consumer inbox dedup is separate.

## 7. Atomicity and error propagation

A PL/pgSQL function that catches WHEN OTHERS and returns false may hide an error from the outer transaction. A caller can then commit earlier writes unless the handler's exception block rolled back all of its own changes and the caller treats false as a mandatory rollback signal. The v2alpha2 integration must choose one of:
- raise a typed exception to abort the outer transaction; or
- return a result enum that the Unit of Work is required to convert into outer rollback, with tests proving no caller can commit a partial result.

Success must include Assertion verification, digest comparison, nonce consumption, state transition, Receipt, Transition and Outbox in one transaction. Failure must roll all of them back. External COMMIT response loss is deliberately deferred to 3.11.4 after these semantics are proven.
