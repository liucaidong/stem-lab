# R03.52.6.2 — Tenant Isolation Architecture Options

- Status: PROPOSED recommendation; DEC-19 remains OPEN
- Decision authority: architecture + security owner
- Product Code Freeze: ACTIVE

## 1. Options

A. Application-enforced tenant isolation: every repository method receives tenant_id and applies predicates; composite tenant keys/FKs supplement. No database RLS reliance.

B. PostgreSQL RLS + trusted application context: API/Worker authorization resolves tenant; a separately trusted issuer produces a short-lived, audience/action/resource-bound assertion; database validates assertion before establishing transaction-local tenant context; RLS filters and checks rows. Plain GUC alone is explicitly insufficient.

C. Database identity / role-based tenant isolation: tenant-specific database role/credential (or isolated schema/database) maps authenticated connection identity to tenant; RLS may remain defense in depth.

## 2. Comparative assessment

| Dimension | A. Application-only | B. RLS + trusted context | C. DB role per tenant |
|---|---|---|---|
| Security strength | Depends on every query/repository; high omission risk | Strong layered enforcement if assertion verification is independent of caller-set GUC | Strong DB identity boundary if credentials/role mapping are isolated |
| Trust assumptions | API code and DB grants fully trusted | Principal resolver, assertion issuer/verifier, DB role and RLS policy trusted | Credential broker, role provisioning and pool routing trusted |
| Operational complexity | Low initially; high review burden | Medium-high; issuer, verifier, key rotation, transaction setup | Very high; role lifecycle, grants, pooling and tenant onboarding |
| Pool compatibility | Easy | Compatible if context is transaction-bound and reset | Difficult with many tenants; pool partitioning/role switching required |
| Performance | Minimal DB policy overhead | Signature verification/context setup + RLS predicate cost | Role switch/pool fragmentation and catalog overhead |
| Scalability | Query discipline degrades with codebase size | Good for many tenants if assertions and RLS are efficient | Role cardinality and connection-pool fragmentation become limiting |
| Failure modes | Missing WHERE clause leaks data | Invalid/missing assertion denies; issuer/verifier outage affects access | Wrong credential/role mapping; pool identity bleed |
| Test complexity | Query-level tests cannot prove all paths | Adversarial DB + pool + issuer tests required | Role matrix, pool routing and credential rotation tests |
| Migration cost | Low | Medium-high; all DB entry paths require context | High; credential and deployment architecture changes |

## 3. Recommendation

Recommend **B as the candidate target**, with A retained as mandatory application authorization and tenant-aware repository predicates. B is defense in depth, not a claim that RLS authenticates users. The trust assertion must be issued only after principal/membership authorization, bound to tenant + subject + audience + action + resource/job + short expiry, and verified by a database-side or otherwise independently trusted boundary before tenant GUC is accepted.

C is a valid higher-isolation option for a small number of high-assurance tenants or dedicated deployments, but is not recommended as the default shared multi-tenant pool until connection cardinality, role lifecycle and cost are benchmarked.

## 4. Required design constraints for B

1. No client-supplied tenant_id becomes trusted context.
2. Job tenant is read from persisted Job row; payload tenant is non-authoritative.
3. Assertion signer is separate from ordinary request parsing and does not accept an unvalidated tenant claim.
4. Worker assertion is bound to the claimed Job, lease owner, epoch, action and audience; it cannot authorize arbitrary tenant-wide access.
5. Assertion expiry is short; nonce/replay policy is explicit.
6. DB runtime role is NOLOGIN/NOSUPERUSER/NOBYPASSRLS, not table owner; no broad DDL or BYPASSRLS.
7. Context installation and queries occur in one transaction; transaction-local settings are mandatory.
8. SECURITY DEFINER is avoided in tenant paths; if needed it must pass a separate security review.
9. All missing, malformed, expired, mismatched or unverifiable contexts deny.
10. System-level access uses a separate principal/capability and audited operation, never a wildcard tenant.

## 5. Decision gates (DEC-19 remains OPEN)

- G1: approve threat model and attacker assumptions.
- G2: choose assertion format and cryptographic profile; evaluate asymmetric signatures vs HMAC and secret custody.
- G3: demonstrate DB-side verification cannot be bypassed by the ordinary application role.
- G4: adversarial PostgreSQL tests for missing/spoofed/expired/replayed/mismatched contexts.
- G5: connection pool commit/rollback/cancellation/context leakage tests.
- G6: Worker claim/renew/complete/fail cross-tenant and stale-fencing tests.
- G7: privileged operation and SECURITY DEFINER review.
- G8: performance and pool exhaustion benchmark.
- G9: migration and rollback plan; named approver and recorded approval.

Until all gates and approval are recorded, DEC-19 = OPEN and B = PROPOSED.
